# Архитектура: локальный клиент, хостинг, WebHID

> Обновлено 2026-11-10 после Goldfish-ревью (4 линзы).
> Отчёт: [`goldfish_arch_review.md`](goldfish_arch_review.md).
> Решение ещё не принято — документ для проверки.

**Область: Windows.** Все замеры и весь реверс сделаны на Windows 11.
Про Linux и macOS в этом документе нет данных — см. §7 R6.

---

## 1. Задача

Сайт, где владелец M62 подключает свою карту и управляет ею, **не
устанавливая M Control Center**.

Ограничение, которое определяет всё остальное: **сервер физически
не видит USB посетителя.** Значит сервер не может управлять
устройством. Он может только раздавать статику.

Отсюда два реальных места, где может жить транспорт:
браузер (WebHID) или процесс на машине пользователя (агент).

---

## 2. Сколько возможностей переносится в браузер

### 2.1 Как считать

Маршрут — это артефакт HTTP, которого в браузере не будет.
Считать надо **возможности** — то, что пользователь теряет или
сохраняет.

Пересчёт: `node src/tools/webhid-coverage-honest.js`.

```
всего маршрутов: 62
доступно в браузере: 48
невозможно: 14

по возможностям: 13 из 17 = 76%
```

**76%, а не 85%.** Прежняя цифра была завышена: скрипт
`webhid-coverage.js` вырезал блоки `try/catch` перед сопоставлением
и засчитывал как доступные пять маршрутов, которые сам документ
объявлял недоступными:

```
GET/POST /api/audio-params   sample rate через UIAutomation
POST /api/eq/open            открывает окно MCC
POST /api/compressor/open    открывает окно MCC
POST /api/compressor/close   закрывает окно MCC
```

Плюс терялась смена режима (`POST /api/mode` останавливает и
запускает MCC).

### 2.2 Доступно в браузере — 13 возможностей

| возможность | через что |
|---|---|
| Громкости (7) | HID `0x2x:0x04`, `0x63/0x64:0x03` |
| Селекторы источников (2) | HID `0x6x:0x02` |
| Настройки устройства | HID `0x11:*` |
| Метры (22) | HID, поток |
| Джеки и зарядка | HID |
| EQ входов | HID `0x91..0x94` |
| EQ наушников | HID `0xa1..0xaa`, только Prof |
| Компрессор | HID `0x46` |
| Реверб | HID `0x44` (см. ловушку в §2.4) |
| Микшер (запись) | HID `0x31..0x3c`, брекетом |
| Loopback | HID `0x51..0x58`, только запись |
| Ducking | HID `0x43`, только запись |
| Режим (чтение) | HID, определение по семействам |

### 2.3 Недоступно — 4 возможности

| возможность | почему |
|---|---|
| **Смена режима** | `POST /api/mode` останавливает MCC, шлёт `0x11:0x1d`, запускает MCC заново из `C:\Program Files\...`. Без MCC устройство остаётся в промежуточном состоянии (NOTES §86) |
| **Профили MCC** | это INI-файлы на диске. См. §7 R7 — браузер МОЖЕТ их читать через File System Access API, это не оценено |
| **Sample rate / buffer** | только клавиатурой UIAutomation; ни в HID, ни в IOCTL их нет |
| **Открытие окон MCC** | по определению — окна нет |

Заметьте: три из четырёх — это машинерия MCC, а не функции устройства.
Пользователю сайта окно MCC не нужно и sample rate нужен редко.
Потеря реально ощутима только в смене режима и профилях.

### 2.4 Три ловушки, без которых 76% не работают

Это не детали реализации — это условия, при которых перечисленные
возможности вообще существуют. Все три уже стоили проекту времени.

**Ловушка 1. Handshake обязателен и идёт ПЕРВЫМ.**

```
0x11:0x01 = 1   один раз, до всего остального
0x11:0x24 = 1   подписка, каждые 2 с
0x11:0x26 = 1   полный дамп: при открытии и повторно каждые 15 с
```

Без handshake устройство отдаёт 44 тега вместо 96+. Без
**повторного** announce не приходят блоки EQ входов (`0x91..0x94`)
и EQ наушников (`0xa1..0xaa`) — они появляются примерно на 19-й
секунде после повторного запроса.

Клиент, который шлёт только подписку каждые 2 с (как в примере
`research/WEBHID.md`), увидит устройство без EQ и сделает вывод
«WebHID не умеет EQ». Это ровно та ошибка, на которую проект уже
потратил месяц.

**Ловушка 2. Микшер пишется только пакетом в брекете.**

```
0x11:0x20 = 1
... ~200 кадров в строгом порядке ...
0x11:0x20 = 0
0x11:0x26 = 1
```

Одиночные записи устройство игнорирует. Порядок критичен: блок →
группа → свойство, группы начинаются с `0x33`, а не по возрастанию.
Проверено совпадением всех 200 адресов с MCC.

**Ловушка 3. Реверб не пишется при `ReverbType = Bypass`.**

Устройство молча игнорирует параметры DryWet/Room/Decay/Width.
Правильный порядок: включить тип (`0x44:0x0b` = 2/3/4), потом
менять параметры. То же верно для дилов в самом MCC (NOTES §71).

**Что из этого следует.** Клиент, который сделает всё правильно,
получит 76%. Клиент, который пропустит любую из трёх ловушек,
получит «ничего не работает» и не поймёт почему. Эти три правила
должны быть в коде с первого дня, а не выясняться отладкой.

### 2.5 Состояние, которое устройство не отдаёт

Микшер, loopback и ducking **только пишутся**. Обратно не приходят
(`IN=0` во всех захватах). Значит их состояние живёт у клиента.

Сейчас в бекенде это `%APPDATA%\m62\state.json`. В браузере аналога
нет — см. §6, это отдельное решение, а не деталь.

## 3. Варианты

### A: WebHID в браузере

`navigator.hid.requestDevice()` по VID/PID `0x152a`/`0x875c`,
`device.open()`, `sendReport(0, frame)` с 16-байтным payload.

**Покрытие:** 13 из 17 возможностей (76%), см. §2.

**Плюсы:** ничего не устанавливать; нет сервера с USB; работает офлайн
как PWA.

**Минусы:** только Chromium; конфликт с MCC (см. R3); таймеры в фоне
(см. R1); разрешение привязано к origin.

### B: локальный агент

Небольшой процесс на машине пользователя, сайт стучится в
`http://127.0.0.1:<порт>`.

**Покрытие:** все 17 возможностей — **но только если MCC установлен**.
Профили и sample rate — это MCC, а не устройство. Без MCC агент даёт
те же 13, что и вариант A.

**Плюсы:** любой браузер; таймеры не зависят от вкладки; можно
добавить файлы, IOCTL, что угодно.

**Минусы:** установка (см. §5 — это дороже, чем кажется); Private
Network Access; антивирусы.

### C: гибрид

WebHID, при неудаче — агент.

**Минусы:** две реализации транспорта. Риск расхождения — как уже
было, когда `state-check.js` и `modes.js` разошлись и один врал на
живом устройстве.

### Упущенные варианты

Ревью справедливо указало, что A/B/C — это одна ось (где живёт
транспорт). Не рассмотрены:

**WebUSB.** Захватывает интерфейс напрямую, не смотрит на usage
pages. У M62 usage = `0x00` (нестандартный), из-за чего в диалоге
Chrome устройство показывается без имени. WebUSB это обходит.
Жизнеспособность не проверена — нужен WinUSB-совместимый дескриптор.
**Не проверено, стоит проверить перед финальным решением.**

**Обёртка Tauri/Electron вокруг текущего бекенда.** Сохраняет 100%
возможностей, убирает проблему фоновых таймеров, не требует
переписывать транспорт. Цена — подписанный установщик и канал
обновлений. Это ровно та цена, которую B платит, но здесь она
не оценена.

**Ограничение, которое делает A единственным вариантом:** если
аудитории нельзя предлагать вообще никакой бинарник, ни установщик,
ни агент. Это сильнее и честнее, чем «сложность низкая/средняя/высокая».
Сказать это прямо — значит сделать рекомендацию опровержимой.

## 4. Сравнение

| | A: WebHID | B: агент | C: гибрид |
|---|---|---|---|
| Установка | нет | да (+ подпись, обновления) | опционально |
| Браузеры | Chromium | любые | Chromium + агент |
| **Возможности без MCC** | **13/17** | **13/17** | 13/17 |
| Возможности с MCC | 13/17 | 17/17 | 17/17 |
| ОС | Windows* | Windows* | Windows* |
| Фоновые таймеры | ломаются | ок | ок |
| Сложность | низкая | высокая | очень высокая |

`*` про Linux — см. R6.

Ключевое, чего не было в прошлой версии: **B не даёт 100%
без MCC.** Профили и sample rate — это сам MCC. Если проект
существует, чтобы его не устанавливать, то B в этих двух пунктах
возвращает зависимость.

## 5. Экономика

Прежняя версия отвергала B словами «надо установить и запустить
процесс» — это звучит как предпочтение, а не как цена. Настоящая цена:

| | A | B |
|---|---|---|
| Написать | порт ядра (§6) + UI | бекенд уже есть + установщик + обновления + UI |
| Выпустить | статика (бесплатно) | подпись кода + SmartScreen-репутация + установщик + канал обновлений |
| Держать | статика + версионирование протокола | то же + обязательства по обновлению агента |
| Поддержка | нет канала отчётов | нет канала отчётов |

**Обязательство, которое не названо:** у статического сайта нет
канала телеметрии. §7 говорит «телеметрия opt-in», но при варианте A
ей некуда идти. Значит при разборе «у меня не работает» не будет
никакого артефакта — только слова пользователя. Это одинаково
плохо в обоих вариантах, и это надо решать отдельно.

**Версионирование протокола.** Прошивка устройства отвечает на
handshake числом (наше отвечает `2`, не `3`). Если выйдет прошивка
с другим протоколом, статический клиент не обновится у тех, у кого
закеширован старый бандл. Нужна проверка версии при подключении и
внятное «ваша прошивка не поддерживается».

## 6. Что именно меняется в бекенде

Проверено чтением кода: `Buffer` встречается только в двух местах.

### 6.1 Портируется БЕЗ изменений (12 модулей)

```
src/crc16.js        CRC-16/MODBUS
src/mixer-tags.js   карта микшера, коды источников
src/eq-hid.js       раскладка EQ входов
src/comp-hid.js     компрессор
src/reverb-hid.js   реверб
src/eq-hp.js        EQ наушников
src/eq-mixer.js     каталог адресов
src/eq-scales.js    шкалы EQ
src/comp-scales.js  шкалы компрессора
src/modes.js        определение режима
src/tags.js         классификация тегов
src/controls.js     громкости и селекторы
```

### 6.2 Портируется ПОСЛЕ правки (1 модуль, 2 строки)

```
src/protocol.js
```

`withReportId()` использует `Buffer.alloc` / `Buffer.from(...).copy(...)`.
В браузере `Buffer` нет. Правится на `Uint8Array` за пять минут:

```js
export function withReportId(frame) {
  const out = new Uint8Array(frame.length + 1);
  out[0] = 0x00;
  out.set(frame, 1);
  return out;
}
```

Это первая функция, которую вызовет браузерный клиент, поэтому
ошибка вылезла бы сразу — но лучше не вылезать.

### 6.3 НЕ портируется: `node-hid`, `fs`, реестр, UIAutomation (4 модуля)

```
src/transport.js        node-hid
src/state-store.js      fs
src/workspace.js        fs + реестр Windows
src/workspace-service.js fs + перезапуск MCC
src/snapshots.js        fs
src/ui-control.js       UIAutomation
src/comp-control.js     UIAutomation
src/eq-control.js       UIAutomation
src/audio-params.js     UIAutomation
src/settings-service.js UIAutomation (только setMode)
```

### 6.4 Главная ошибка прошлой версии: transport.js — это не «только node-hid»

Утверждение «`transport.js` в браузере не нужен» неверно. В нём
только **открытие устройства** привязано к Node. Всё остальное —
обычный JS, и это выстраданные исправления:

- **Батчевое чтение** (`BATCH = 64`): наивное «один отчёт за тик»
  теряло 80% пакетов — 262 чтения за 4 с вместо 2048, настроек
  2/8 вместо 8/8.
- **Keepalive 2 с** и **периодический announce 15 с**.
- **Оптимистичный кеш после записи**: устройство не подтверждает
  запись, следующий дамп приходит поздно (а для EQ — раз в сессию).
  Без обновления кеша второй вызов читает старое значение и
  отказывает. Именно на этом реверб «не работал».
- **Фильтр idle-отчётов** (`isIdle`).
- **Переподключение с backoff**.

Правильное деление: **политика транспорта** (портируется) отдельно
от **адаптера устройства** (`node-hid` сейчас, `navigator.hid` потом).
Это единственная граница, которая нужна.

### 6.5 Логика, живущая в server.js, а не в модулях

`server.js` — не «обвязка». В нём накоплено то, что придётся
повторять браузерному клиенту:

- разбор ключей кеша в двух форматах (hex и decimal) — `snapshotValue`;
- разрешение `delta` против `value` с отказом 409, когда текущее
  значение неизвестно;
- правило оптимистичного кеша;
- проверка согласованности режима (файл против HID).

Это надо переносить, а не «переписывать с нуля».

## 7. Риски

### R1. Таймеры в фоновой вкладке — не решено

Три таймера: handshake (один раз), подписка 2 с, announce 15 с.
Chrome душит таймеры в скрытых вкладках до раза в минуту. Все три
умрут одновременно, и поток прекратится **молча**.

Прежняя версия предлагала `navigator.wakeLock`. **Это не работает**:
wakeLock удерживает экран от выключения и освобождается, как только
документ становится скрытым — то есть именно в том сценарии, от
которого защищает.

Web Worker частично помогает (таймеры там душатся меньше), но
`requestDevice()` доступен только в Window. Значит: разрешение
получаем в окне, затем передаём устройство в воркер, который
становится единственным владельцем. Это архитектурное решение,
и его надо принять до кода.

**Что остаётся, если оба не сработали:** предупреждать пользователя
«не уходите со вкладки» и восстанавливать сессию при возврате
(повторный handshake и дамп). Это плохой UX, но честный.

**Это надо измерить, а не предполагать.** §8 требует прогона
в скрытой вкладке.

### R2. Разрешение привязано к origin

Выдаётся один раз на домен. Сменился домен — заново. Не блокер.

### R3. MCC конфликтует — и это ХУЖЕ, чем «не откроется»

Прежняя версия говорила: «WebHID может не открыть устройство, надо
показать ошибку». Опасный случай **обратный**: устройство
открывается (MCC можно читать параллельно), запись проходит, но
**MCC её откатывает**.

Замерено: с запущенным MCC запись `0x46:02 = -28` не применялась
60+ секунд; без MCC — 10 секунд.

То есть пользователь увидит «сохранено», а устройство останется
на старом значении. У браузера нет серверного цикла
«переподключись и перечитай», так что это надо строить в клиенте.

**Минимум:** после записи запросить свежий дамп (новой подпиской,
а не из кеша — кеш в той же сессии врёт) и, если значение
не изменилось, показать «M Control Center конфликтует, закройте его»,
а не «успех».

### R4. Безопасность: страница получает доступ к железу

Разрешение постоянное и на origin. Значит: один XSS на странице —
это возможность писать произвольные кадры в устройство пользователя.
Сторонний скрипт наследует доступ. Origin, сменивший владельца,
сохраняет разрешение.

**Требования:** никакого стороннего JS на странице управления; CSP;
кадры строятся только из кода протокола, никогда из данных сервера.
Это же аргумент за маленький аудируемый бандл.

### R5. Мультипользовательность — не свойство варианта

Прежняя версия утверждала, что «каждый управляет своей картой»
работает только в A. Это работает и в B: сайт плюс агент у каждого
пользователя — тоже одна карта на человека.

**Настоящее свойство задачи:** никакой сервер не видит устройства.
Это следует из физики, а не из выбранного варианта.

### R6. Linux и macOS — не проверялись

На Linux доступ к HID идёт через `hidraw` и требует udev-правила
или членства в группе. Это системная настройка, которую **сайт
сделать не может**. Значит формулировка «просто зайти на сайт»
верна только для Windows.

Либо явно ограничить проект Windows, либо добавить это в список
того, что пользователь делает руками.

### R7. «Браузер не имеет доступа к файлам» — неверно

Прежняя версия утверждала, что профили MCC недоступны, потому что
браузер не видит файлы. Это не так: File System Access API
(`showDirectoryPicker`) даёт доступ к выбранной папке, с сохранением
разрешения между сессиями.

То есть профили **читаемы и записываемы** в варианте A, если
пользователь укажет папку `C:\Program Files\TOPPING Pro\...\Workspace`.
Жест доверия тот же, что и для устройства.

Это не значит, что надо так делать — но это надо было оценить,
а не объявлять невозможным. Если решено не делать, причина должна
быть записана: лишний запрос разрешения, необходимость искать
папку в `Program Files`, риск записи в чужую программу.

## 8. Что не решено

1. **Какой вариант.** Нужно решение.
2. **Где живёт состояние микшера, loopback и ducking.** См. §6.5 —
   это отдельное решение, не деталь.
3. **Как обрабатывать обрыв связи.** `navigator.hid` шлёт `disconnect`.
   Что показывать, как восстанавливаться — не описано.
4. **WebUSB** — проверить, обходит ли он проблему usage = 0x00.
5. **File System Access** для профилей — оценить или отвергнуть
   с причиной.
6. **Канал отчётов об ошибках** — при статике его нет.

## 9. Что делать до фронтенда: проба WebHID

Маленькая страница. Пока она не пройдена, всё остальное — теория.

**Условия:** Windows, Chrome, MCC **полностью закрыт** (не в трее).

**Проверки — каждая да/нет, без «выглядит работающим»:**

1. `requestDevice()` показывает M62 в списке.
2. `device.open()` проходит без ошибки.
3. После handshake `0x11:0x01 = 1` устройство отвечает.
4. Первый дамп даёт **≥ 90 тегов**, среди них `0x91:*` (EQ входов).
5. После **повторного** announce (через 15 с) приходят `0xa1:*`
   (EQ наушников) — в Prof-режиме.
6. Запись громкости применяется и видна в **новой подписке**.
7. Сессия живёт **60 секунд в скрытой вкладке** (переключиться
   на другую вкладку и вернуться) — поток не прервался.
8. Запись при **запущенном** MCC: видно, откатилась ли она.
   Это проверяет R3 на практике.

Если пункты 1–6 проходят, а 7 нет — вариант A работает только
в активной вкладке, и это надо принять явно.
Если 8 показывает откат — нужна детекция конфликта, как в R3.

## 11. Рекомендация

**Вариант A для первой версии**, при явном ограничении «Windows,
Chromium, никакого бинарника».

Причины:
- 13 из 17 возможностей без установки — это и есть ценность идеи;
- оставшиеся 4 — машинерия MCC (3 из 4) и смена режима;
- реверс уже позволяет: EQ, компрессор, реверб, микшер пишутся
  через HID;
- B не даёт выигрыша без MCC, а с MCC возвращает зависимость,
  от которой проект уходит.

**Что должно быть верно, чтобы это решение устояло:**
- проба §9 проходит (особенно пункты 4, 5, 7);
- состояние микшера можно хранить в браузере без потери данных
  (см. §6.5 — пока не решено);
- Windows-only приемлемо.

Если проба провалится по пункту 7, честный ответ — клиент работает
только в активной вкладке, либо вариант B/обёртка.
