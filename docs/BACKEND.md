## Архитектура: каналы данных

> **Обновление 2026-11-08.** Прежняя формулировка «микшер и EQ недоступны
> через HID вообще» **опровергнута**. Ниже — актуальное состояние.

Устройство отдаёт состояние **несколькими путями**:

| канал | что там | модуль |
|---|---|---|
| **HID** | громкости, селекторы, метры, джеки, настройки, FX-уровни, **компрессор**, **EQ (чтение)**, реверб | `transport.js` |
| **workspace-файл** | микшер, EQ (запись), входы (48V, GAIN, MIC), loopback, outputs, ducking | `workspace-service.js` |
| **UI M Control Center** | реверб (4 типа), компрессор (альтернативный путь записи) | `ui-control.js` |
| **IOCTL драйвера** | версии, sample rates | `research/dis/*` |

### Что действительно верно

- **Микшер** — адреса в HID известны (`0x31..0x36`), но канал **не отвечает**
  ни на чтение, ни на запись. Практически только INI + MCC.
- **EQ-полосы** — **читаются из HID** (`0x91..0x94`) после handshake.
  Запись через HID не подтверждена; через INI — работает.
- **Компрессор** — **пишется через HID** (`0x46:0x02..0x08`), но применяется
  отложенно. Проверять результат надо по INI, а не по немедленному ANNOUNCE.
- **Thesycon DSP-путь** (IOCTL `0x80882200`/`0x80882204`) — **неработоспособен**:
  DSP-плагина нет на машине, и таблицы property ID не существует в принципе.

## Жизненный цикл транспорта

1. Найти HID interface 4 (`VID 0x152A`, `PID 0x875C`).
2. Открыть.
3. **`TT=0x11, PP=0x01, value=1` — session handshake (ОБЯЗАТЕЛЕН).**
   Без него: 44 тега вместо 96…102, компрессор и EQ не приходят вообще.
4. Отправить `TT=0x11, PP=0x24, value=1` — **подписка**.
5. Отправить `TT=0x11, PP=0x26, value=1` — **запрос состояния**.
6. Стартовать keepalive: каждые **2000 мс** повторять подписку.
7. Читать отчёты **пачками** (см. ниже).
8. Отбрасывать холостые (16 нулей), парсить, класть в кеш, рассылать.

**Без keepalive устройство замолкает.** Без handshake — состояние неполное.

### Критично: чтение пачками

Наивный вариант «одно чтение за тик `setTimeout(_, 0)`» даёт ~65 тиков/сек,
а устройство шлёт сотни отчётов. В результате терялось ~80% потока
и приходило 2 настройки из 8 вместо всех.

**Исправлено** в `#startReading()`: внутри одного тика вычитывается
пачка до 64 отчётов с `readTimeout(5)`.

| реализация | чтений за 4 с | параметров | настроек |
|---|---|---|---|
| было: 1 чтение за тик | **262** | 26 | **2/8** |
| стало: пачка за тик | **2048** | 51 | **8/8** |

### Критично: ANNOUNCE нужен ровно один

Устройство присылает настройки только в ответ на `0x11:0x26`, причём
**один запрос — одна порция**. Частые запросы подряд **сбивают** ответ.

| метод | результат |
|---|---|
| 1 запрос + пауза 3 с | **8/8** тегов |
| 3 запроса по 1 с | **0/8** тегов |

## Метры уровня

22 адреса. Значения меняются постоянно — это **не состояние**, а поток.

| тег | что |
|---|---|
| `0x21:0x01` | IN1 |
| `0x25:0x01` | BT |
| `0x31:0x15`, `0x32:0x15` | выходы |
| `0x33:0x15`…`0x36:0x15` | каналы 1–4 |
| `0x39:0x01`, `0x39:0x02` | метры |
| `0x44:0x0d`, `0x44:0x0e` | FX in/out |
| `0x46:0x09`, `0x46:0x0a`, `0x46:0x0c`, `0x46:0x0d` | компрессор |
| `0x61:0x01`, `0x62:0x01` | OTG out L/R |
| `0x63:0x01`, `0x64:0x01` | HP L/R |
| `0x9b:0x0b` | EQ |

**Шкала расшифрована:** `дБ = raw / 10`, диапазон **−90.2 … 0 dB**,
пол `raw = −902`. Наклон проверен на 8-дБ интервалах: 10.25 / 10.00 / 9.88
raw на дБ.

Особые случаи:

| тег | поведение |
|---|---|
| `0x46:0x09` (`comp9`) | константа −800 |
| `0x46:0x0a` (`comp10`) | всегда 0, не используется |

**Редукция компрессора:** `GR = (comp13 − comp12) / 10`, где `comp12` — до
сжатия, `comp13` — после. Проверено на железе.

Приходят сами, без запроса — когда играет звук.

**Для фронта:** это основной поток событий. Нужен отдельный буфер
и троттлинг отрисовки. Готовый разбор — `GET /api/meters` (все метры в дБ
одним запросом, с флагами `atFloor` / `noData` / `ageMs`).
