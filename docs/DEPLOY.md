# Как развернуть сайт (хостинг)

> Обновлено 2026-11-19. Для владельца проекта и всех, кто хочет
> поднять свой экземпляр.

## Что вообще хостится

**Статика: один HTML-файл и 17 JS-модулей.** Всё.

Сервер **не управляет картой**. Управление идёт из браузера через
WebHID: пользователь заходит на сайт, нажимает «Подключить», браузер
спрашивает разрешение, дальше страница говорит с картой напрямую.

```
пользователь ──► сайт (статика) ──► WebHID ──► его M62
```

Данные пользователя **не покидают его компьютер**.

## Требования к сайту

| требование | почему |
|---|---|
| **HTTPS** | без него браузер не даёт `navigator.hid` (кроме localhost) |
| Chrome / Edge 89+ | Firefox и Safari WebHID не умеют |
| Десктоп | WebHID нет на Android и iOS |

Всё остальное — обычный статик-хостинг.

## Быстрый старт локально

```bash
npm install
npm start
# открой http://127.0.0.1:8080/
```

`npm start` поднимает `src/static-server.js` — минимальный сервер,
который отдаёт только сайт.

## Что внутри сервера

`src/static-server.js`, ~520 строк:

- **белый список файлов** — 18 путей, перечисленных поимённо;
- заголовки безопасности (CSP, nosniff, frame-deny);
- **сжатие** gzip/brotli: 132 КБ → 36 КБ (72% экономии);
- **ETag** — повторный визит не скачивает файлы (304);
- **healthcheck** `/health` для Docker/K8s/Cloudflare;
- таймауты против медленных клиентов (slowloris);
- опциональный access-log в формате nginx;
- graceful shutdown по SIGTERM (работает на Linux/Docker).

Серверный код (`research/dev-server/server.js` с 61 маршрутом, `src/transport.js`,
`workspace.js`, `ui-control.js`) **не отдаётся** — это проверяется
тестом.

## Переменные окружения

| переменная | по умолчанию | зачем |
|---|---|---|
| `PORT` | `8080` | порт. `0` = любой свободный (для тестов) |
| `HOST` | `0.0.0.0` | адрес прослушивания |
| `M62_ACCESS_LOG` | выкл | `1` — писать по строке на запрос |

Access-log в формате nginx:

```
203.0.113.42 - [19/Nov/2026:02:55:00 +0000] "GET / HTTP/1.1" 200 5113 "-"
```

IP берётся из `X-Forwarded-For`, если запрос пришёл через прокси —
свой адрес там бесполезен.

## Производительность

| файл | без сжатия | brotli |
|---|---|---|
| `/` (HTML) | 21 039 | 5 123 |
| `/app.js` | 53 205 | 12 683 |
| `/src/transport-core.js` | 19 293 | 5 619 |
| **вся страница** | **93 537** | **23 425** |

Экономия 75%. Повторный визит — ещё дешевле: браузер получает `304`
без тела.

## За обратным прокси

Сервер проверен за nginx/Caddy (тест `test-behind-proxy.js`, 20/20):

- заголовки безопасности не дублируются (проверяется поимённо);
- `content-length` совпадает с телом, в том числе после сжатия;
- `Vary: accept-encoding` на месте — прокси не отдаст gzip
  непонимающему браузеру;
- `X-Forwarded-For` и `X-Forwarded-Proto` не ломают ответ.

**HSTS сервер не отдаёт намеренно** — это задача прокси. На `http`
HSTS бессмыслен, а браузер запоминает его навсегда.

## Устойчивость

Проверено `test-static-robustness.js` (14/14):

- 16 типов мусорных URL (обход каталога, `.env`, `/wp-admin`, NULL-
  байты) → 400/404;
- URL на 60 000 символов → 431 (встроенная защита Node);
- 100 одновременных запросов обслужены за ~90 мс;
- медленные клиенты (slowloris) не блокируют остальных;
- после всех атак сервер работает нормально.

Таймауты: заголовки 10 с, запрос 30 с, keep-alive 5 с.

## Graceful shutdown: различие платформ

На Linux и в Docker SIGTERM вызывает обработчик, сервер доотдаёт
текущие ответы и закрывается с кодом 0.

**На Windows этого не происходит:** Node не реализует SIGTERM/SIGINT
как «мягкие» сигналы, `kill()` убивает процесс сразу. Проверено
`diag-signals.js`. Это ограничение ОС, а не сервера; на проде
(Linux) всё работает как надо.


## Почему два сервера

| файл | для чего | нужен на хостинге |
|---|---|---|
| `src/static-server.js` | отдать сайт | **да** |
| `research/dev-server/server.js` | агент: workspace, UIA-управление MCC, API на 61 маршрут | **нет** |

`research/dev-server/server.js` — это инструмент разработки и исследований. Он тянет
`node-hid`, `ws` и Windows-специфику. На хостинге он не нужен и
вреден: увеличивает поверхность атаки.

## Варианты развёртывания

### Вариант 1: любой статик-хостинг (проще всего)

Подойдёт GitHub Pages, Cloudflare Pages, Netlify, Vercel,
обычный nginx.

**Сайт работает и в корне домена, и в подкаталоге.** Пути
относительные (`./app.js`, `../src/x.js`), поэтому GitHub Pages
с его `user.github.io/repo/` тоже подходит.

Нужно отдать эти файлы:

```
/                    -> index.html   (лежит В КОРНЕ репозитория)
/app.js              -> app.js
/mixer-state.js      -> mixer-state.js
/scenes.js           -> scenes.js
/src/*.js            -> 15 модулей
```

**Почему страница в корне.** GitHub Pages, Cloudflare Pages и любой
`npx serve` раздают каталог как есть: `index.html` ищется в корне и
никаких алиасов нет. Пока страница лежала в `web/`, главная по
адресу сайта отдавала 404 — при том что на нашем сервере всё
работало, он умел алиас `/` -> `web/index.html`.

Проверяется это не нашим сервером, а отдельно:
`node src/tools/check-plain-static-hosting.js` поднимает «глупую»
раздачу каталога без алиасов и смотрит, что страница и все её
импорты открываются.

Полный список — `ALLOWED_FILES` в `src/static-server.js` (21 URL).

### Вариант 2: свой сервер

```bash
PORT=8080 node src/static-server.js
```

Дальше — любой reverse-proxy с сертификатом (nginx, Caddy).
Caddy проще всего: сам получает HTTPS.

```
m62.example.com {
    reverse_proxy 127.0.0.1:8080
}
```

### Вариант 3: Docker

```dockerfile
FROM node:20-alpine
WORKDIR /app
COPY package.json ./
RUN npm install --omit=dev
COPY src/static-server.js src/static-server.js
COPY src/*.js src/
COPY index.html app.js mixer-state.js scenes.js ./
ENV PORT=8080
EXPOSE 8080
CMD ["node", "src/static-server.js"]
```

## Проверка ПОСЛЕ публикации

Когда сайт уже развёрнут, проверьте, что хостинг отдаёт всё правильно:

```bash
node src/tools/verify-deployed-site.js https://m62.example.com/
node src/tools/verify-deployed-site.js https://user.github.io/repo/
```

Второй вариант — для хостинга в **подкаталоге** (GitHub Pages).

Скрипт идёт по графу модулей и проверяет то, что ломается только на
живом домене:

| проверка | почему важна |
|---|---|
| HTTPS | без него браузер не даст доступ к карте |
| все 15 модулей отдаются | один 404 рушит всю страницу |
| CSP сохранён | некоторые хостинги переписывают заголовки |
| сжатие включено | иначе страница грузится в 4 раза дольше |
| серверный код не виден | `/research/dev-server/server.js` и `/package.json` должны быть 404 |

Ожидаемый результат — 17 проверок, 0 провалов:

```
  пройдено:  17
  провалено: 0
  САЙТ РАЗВЁРНУТ КОРРЕКТНО.
```

Проверено контрпримером: на dev-сервере (без CSP и сжатия) скрипт
честно показывает 3 провала.

**Что остаётся проверить руками** — работу с реальной картой. WebHID
требует видимого окна и выбора устройства в диалоге, поэтому
автоматически это не проверяется. После запуска скрипта откройте сайт
в Chrome/Edge и нажмите «Подключить».

## Проверка ПЕРЕД публикацией

```bash
npm run check
```

Это линтер + все офлайн-тесты + тесты статик-сервера. Проверяет в том
числе, что:
- все файлы из белого списка существуют;
- серверный код не отдаётся;
- обход каталога заблокирован;
- заголовки безопасности на месте;
- нет BOM (иначе `npm` сломается на `package.json`);
- Dockerfile копирует все нужные файлы.

Отдельно можно проверить то же, что делает CI при сборке контейнера:

```bash
npm run ci:simulate
```

## Автоматические проверки (CI)

`.github/workflows/ci.yml` запускается на каждый push и pull request.
Три задачи:

| задача | что делает |
|---|---|
| **Тесты (Ubuntu, Node 20 и 22)** | линтер, офлайн-тесты, тесты сервера, проверка BOM |
| **Тесты (Windows)** | то же — ловит платформенную специфику |
| **Docker** | собирает образ, запускает контейнер, проверяет `/health`, сжатие и что серверный код не отдаётся |

Почему две ОС: Ubuntu ближе к проду (там работают сигналы и Docker),
а Windows — где идёт разработка (там ловятся BOM, пути, отличие
SIGTERM).

Тесты на живом устройстве (`test-transport-core.js` и `prove-*`) в CI
**не запускаются**: им нужна подключённая M62. Они запускаются
локально командой `npm run test:device`.

## Проверка конфигурации

Локально Docker нет — шаг со сборкой образа проверить нельзя. Но
логику его smoke-тестов (`/health`, сжатие, отсутствие утечек)
повторяет `npm run ci:simulate`. Если он проходит, значит и в CI
пройдёт.


## Чего НЕ будет работать у пользователя

Честно говорим на странице:

| что | почему |
|---|---|
| Firefox, Safari | нет WebHID |
| Телефоны, планшеты | нет WebHID |
| `http://` кроме localhost | браузер блокирует HID |
| Чтение микшера | карта не отдаёт его по протоколу |
| Подтверждение записи в тишине | метры только при звуке |

## Безопасность: что мы гарантируем

- Сайт не отправляет данные карты на сервер — их физически нет в
  запросах.
- Нет аналитики, нет внешних скриптов (CSP это запрещает).
- Сервер отдаёт только 17 известных файлов.
- Обход каталога заблокирован (проверено тестом).
