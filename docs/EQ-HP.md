> Расшифровано 2026-11-08 в Prof-режиме.
> Разбор: `src/tools/analyze-eq-hp.py`, `dump-slow.js`, `test-eq-hp-bulk.js`.

## Главная находка: 100 тегов `0xa1..0xaa`

Блоки, которые не приходили ни в Live, ни в Mobile:

```
0xa1 .. 0xaa   10 блоков по 10 свойств = 100 тегов
0xab           2 тега (0x0f, 0x14)
```

Всего в Prof-режиме **177 адресов** против 100 в Live и 95 в Mobile.

## Что это такое

**EQ наушников, 10 полос × 2 канала.** Подтверждено скриншотом окна MCC:
в нём ровно 10 полос, у каждой Type / Gain / Freq / Q — и значения
совпадают с тегами один в один.

| в окне | тег | значение |
|---|---|---|
| Type = peaking | `02` / `07` = 1 | 1 = peaking |
| Gain = 0.0 | `03` / `08` = 0 | дБ |
| Freq = 632 | `04` / `09` = 632 | Гц |
| Q = 0.707 | `05` / `0a` = 7070 | × 10000 |
| чекбокс не отмечен | `01` / `06` = 0 | 0 = выкл |

## Структура

```
0xa1 = полоса 1     0xa2 = полоса 2   ...   0xaa = полоса 10

свойства 01..05 = ЛЕВЫЙ канал
свойства 06..0a = ПРАВЫЙ канал

  01 / 06  вкл-выкл полосы      0/1
  02 / 07  тип фильтра          1 = peaking
  03 / 08  gain, дБ
  04 / 09  частота, Гц
  05 / 0a  Q × 10000
```

Структура **идентична EQ входов** (`0x91..0x94`): там тоже 2 полосы × 5 полей
на блок. То есть протокол EQ единый, просто в Live 4 блока (2 канала × 2 полосы),
а в Prof 10 блоков (10 полос наушников).

`0xab:0x0f` и `0xab:0x14` — вероятно служебные (GainOutput, состояние EQ).
В `[EQ_HP]` из INI есть `GainOutput=-50` и `EQState*` — похоже на них.

## ВАЖНО: тайминг в Prof-режиме

Блоки `0xa1..0xaa` приходят **поздно**:

```
~560 мс    метры, 0x9b, 0x33..0x36:0x15
~3900 мс   0x12 (инфо)
~4850 мс   0x11 (настройки)
~7240 мс   0x91..0x94 (EQ входов)
~7320 мс   0xa1..0xaa (EQ наушников)   ← 7.3 с!
~7520 мс   0xab
~7550 мс   джеки, 0x22/0x23/0x25
```

**Два следствия:**

1. **Окно снимка — не меньше 16 секунд.** Мой прежний `dump-mode.js`
   слушал 7.5 с и иногда ловил только часть блоков (168 из 177).

2. **Пауза между сессиями — не меньше 3 секунд.** Проверено:

```
пауза 0 с    -> 30 адресов,  0xa1 нет
пауза 0.9 с  -> 28 адресов,  0xa1 нет
пауза 3 с    -> 175 адресов, 0xa1 на 8.2 с
пауза 5 с    -> стабильно
```

В Live хватало 500 мс. В Prof нужно 3+ с — вероятно потому, что
блоков больше и устройство дольше готовит дамп.

## Запись EQ наушников РАБОТАЕТ

Проверено контрольным опытом (2026-11-08):

```
окно EQ ОТКРЫТО:   A прямая  40 -> 20  ПРИНЯТО
                   B брекет  40 -> 20  ПРИНЯТО
                   C +save   40 -> 20  ПРИНЯТО

окно EQ ЗАКРЫТО:   прямая    40 -> 30  ПРИНЯТО
```

**Все способы работают, окно не нужно.** Достаточно обычного
`send(0xa1, 0x03, значение)`.

### Почему раньше казалось, что не работает

Ошибка в методе измерения, не в железе. Снимок после записи был
**неполным**: в Prof блоки `0xa1..0xaa` приходят на **7–11 секунде**,
а я слушал 7.5–16 с и иногда не дожидался. «Не принято» на самом деле
означало «не увидели» — тег вообще отсутствовал в снимке (`undefined`),
а не оставался старым.

Правильный тайминг для Prof:

```
пауза между сессиями:   5 с
окно прослушивания:     26 с
после открытия окна EQ: 20 с (MCC занят, иначе приходит 30 адресов вместо 177)
```

С этими параметрами `0xa1` приходит стабильно (10.8–11.6 с),
и запись видна сразу.

### Подтверждение связи «полоса → блок»

Через UI: 4 нажатия стрелки вверх на диле Gain полосы 1 дали
`0xa1:03 = 40` (было 0). Это доказало, что `0xa1` — именно полоса 1,
а `03` — именно Gain. Прямая запись того же тега даёт тот же эффект.

## Ещё одна ловушка: окно EQ — отдельное окно

Окно EQ наушников **не** является частью `MainWindow_M62`:

```
AutomationId дилов:  QApplication.EQ_HP.contentWidget.mWidget.EQ_HP...
                     ^^^^^^^^^^^^^^^^^^
                     НЕ "MainWindow_M62"!
```

Поэтому поиск по `AutomationId -match "Equalizer"` его не находил.
Правильно: `AutomationId.StartsWith("QApplication.EQ_HP")`.

Координаты дилов (при 1666×1006):

```
x = 452, 534, 616, 698, 780, 862, 944, 1026, 1108, 1190   (10 полос)
y = 593 (Gain), 671 (Freq), 749 (Q)
```

## Тоже ловушка: окно может быть свёрнуто

Если `GetWindowRect` возвращает `-32000,-32000` — окно в трее.
Клики уходят в пустоту, хотя `Invoke`/`SetFocus` рапортуют успех.

Лечение:

```powershell
[Wnd]::ShowWindow($h, 9)   # SW_RESTORE
Start-Sleep -Milliseconds 800
[Wnd]::SetForegroundWindow($h)
```
