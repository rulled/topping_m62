# M62 Web Client — что доступно (для дизайнера)

Документ описывает **только факты о данных**: какие параметры существуют,
какие у них диапазоны, единицы, состояния и события. Никаких решений о виде
интерфейса здесь нет и быть не должно.

Источник: mainline-драйвер `hid-topping` + реверс `M Control Center` +
публичная документация [NTMan/topping-m62](https://github.com/NTMan/topping-m62).
Прошивка `V87.05.45.48.27`.

> **Обновление 2026-11-08.** Главное изменение: найден **session handshake
> `11/01 = 1`**. Без него бекенд получал 44 параметра, с ним — **96…102**.
> Именно он раскрыл компрессор и EQ-полосы, которые раньше считались
> недоступными. Handshake уже встроен в транспорт, фронту делать ничего
> не нужно — но знать про это важно, потому что «пустые» блоки в старой
> документации теперь заполнены.

## 1. Общая модель

Устройство — USB-аудиоинтерфейс. Управление идёт по отдельному HID-каналу.

**Ключевые свойства модели:**

1. **Устройство присылает события, а не состояние.** Оно сообщает о том, что
   *произошло* (повернули ручку, вставили джек), а не о том, что *есть*.
2. **Селекторы источников не читаются вообще.** У них нет физической ручки,
   поэтому устройство про них не сообщает.
3. **Подписка истекает.** Клиент обязан продлевать её каждые 2 секунды, иначе
   поток событий прекращается.
4. **Нужен session handshake.** При подключении клиент отправляет
   `11/01 = 1` и ждёт ответа, иначе часть состояния (компрессор, EQ) не
   придёт вообще.
5. **После подключения состояние приходит двумя волнами:** примерно через
   0.9 с и примерно через 5.2 с.
6. **Запись применяется отложенно.** Устройство не подтверждает запись;
   значение фиксируется при следующем цикле синхронизации. Фронт не должен
   ждать ACK — оптимистичное обновление экрана корректно.

### 1.1 РЕЖИМ УСТРОЙСТВА МЕНЯЕТ СОСТАВ ЭКРАНОВ

У M62 три режима, и **набор доступных блоков в них разный**:

| | Mobile | Live streaming | Pro audio |
|---|---|---|---|
| Микшер | **нет** | 5 шин (A–E) | 3 шины (A–C) |
| Loopback | **нет** | 4 канала | 4 канала |
| Эффекты (NC, реверб) | есть | есть | **нет** |
| EQ микрофонов (4 полосы) | **нет** | есть | нет |
| EQ наушников (10 полос) | нет | **нет** | **есть** |
| Ducking | есть | есть | **нет** |
| Компрессор | есть | есть | есть |

> Дизайнеру: **интерфейс не может быть статичным.** Число шин микшера,
> наличие EQ и loopback зависят от режима. Нужно уметь перестраиваться
> или скрывать недоступное.

**Режим не читается из устройства** (тег `0x11:0x1d` оно не возвращает).
Бекенд определяет его косвенно — по имени папки workspace и составу блоков.
Отдаётся в `GET /api/mode`:

```json
{
  "mode": "Live",
  "confidence": "high",
  "capabilities": { "mixerBuses": 5, "effects": true, "eqHeadphone": false },
  "actual": { "mixerChannels": 10, "loopbackCount": 4, "eqBlocks": ["EQ_IN1","EQ_IN2"] }
}
```

**Смена режима перезагружает устройство** на 1–8 секунд — соединение
пропадает. После перезагрузки меняется и активный workspace-файл.

## 2. Параметры

### 2.1 Громкости — 7 штук

Все — целые числа. **Индекс 0 = полная тишина (mute), максимум = максимум.**

| параметр | диапазон | направление | шаг кривой |
|---|---|---|---|
| Mic-1 Analog Capture Volume | 0..88 | вход | 1.00 dB |
| Mic-2 Analog Capture Volume | 0..88 | вход | 1.00 dB |
| Aux Capture Volume | 0..99 | вход | 3 сегмента, см. ниже |
| Bluetooth Capture Volume | 0..99 | вход | 2 сегмента, см. ниже |
| OTG Capture Volume | 0..99 | вход | 2 сегмента, см. ниже |
| Headphone Playback Volume | 0..99 | выход | 3 сегмента, см. ниже |
| OTG Playback Volume | 0..99 | выход | 2 сегмента, см. ниже |

**Важно:** диапазоны **разные**. У Mic-1 и Mic-2 — `0..88`, у остальных — `0..99`.

#### Кривые (для отображения в дБ)

Кривая **нелинейная**. Значение индекса → дБ считается по сегментам:

**Тип A** (Aux, Headphone):
```
индекс 0      -> MUTE
индекс 1..19  -> от -88.00 dB, шаг 2.00 dB
индекс 20..61 -> от -51.00 dB, шаг 1.00 dB
индекс 62..99 -> от  -9.50 dB, шаг 0.50 dB
```

**Тип B** (Bluetooth, OTG IN, OTG OUT):
```
индекс 0      -> MUTE
индекс 1..79  -> от -88.00 dB, шаг 1.00 dB
индекс 80..99 -> от  -9.50 dB, шаг 0.50 dB
```

**Тип C** (Mic-1, Mic-2):
```
линейно, шаг 1.00 dB на единицу индекса
```

> Дизайнеру: слайдер по «сырому» индексу будет ощущаться неравномерно.
> Нужно решить, показывать ли дБ, проценты или индекс.

### 2.2 Селекторы источников — 2 штуки

| параметр | что выбирает |
|---|---|
| Headphone Playback Source | куда слушает выход на наушники |
| OTG Playback Source | куда слушает OTG-выход |

**Доступные варианты (15 штук):**

| отображаемое имя | значение |
|---|---|
| Unknown | 0 |
| Mix A | 1 |
| Mix B | 2 |
| Mix C | 3 |
| IN 1 | 6 |
| IN 2 | 7 |
| IN 1+2 | 8 |
| AUX | 9 |
| BT | 10 |
| OTG IN | 11 |
| Playback 1/2 | 12 |
| Playback 3/4 | 13 |
| Playback 5/6 | 14 |
| Playback 7/8 | 15 |
| Playback 9/10 | 16 |

**КРИТИЧНО ДЛЯ ДИЗАЙНА — три особенности:**

1. **`Unknown` — это не выбор.** Это состояние «никто ничего не выбирал».
   При старте селектор всегда в нём.

2. **Селектор нельзя прочитать.** Если приложение не записало значение само,
   оно **не может узнать**, куда указывает выход. Вендорское приложение
   решает это тем, что **шлёт свой workspace целиком** при подключении.

3. **Селектор решает, будет ли звук вообще.** Он не зависит от того, какой
   PCM-поток играет хост. Ситуация: хост играет в `Playback 1/2`, а выход
   слушает `Mix C` — карта работает корректно, но играет из источника,
   который никто не наполняет. **Со стороны хоста нет никаких признаков,
   почему тишина.** Устройство автономное (на батарее), поэтому на свежей
   системе оно наследует то, что оставило последнее приложение.

### 2.3 Эквалайзеры — 3 штуки. ДОСТУПНЫ через workspace-файл

**Обновлено 2026-11-07:** ранее я писал, что EQ недоступен. Это было
неверно — EQ **есть**, но не в HID-канале, а в workspace-файле MCC.
Подробно: `research/WORKSPACE.md`.

| эквалайзер | полос | откуда берётся |
|---|---|---|
| EQ_IN1 | 4 | `[EQ_IN1]` в workspace |
| EQ_IN2 | 4 | `[EQ_IN2]` в workspace |
| EQ_HP (наушники) | 10 | только в Pro audio mode |

**Что есть по каждой полосе (факт, из файла):**

| поле | пример | смысл |
|---|---|---|
| тип | `0` | тип фильтра (peaking/lowpass/highpass/lowshelf/highshelf — соответствие номеров не установлено) |
| частота | `632` | Гц |
| Q | `0.7` | добротность |
| gain | `0` | дБ |

Плюс на весь EQ: `Switch` (вкл/выкл) и `GainInput`.

**Что даёт HID (после session handshake `11/01`):**

Блок `0x91..0x94` отдаёт по **10 значений** — это **2 полосы × 5 полей**:

```
0x01..0x05  — полоса 1
0x06..0x0a  — полоса 2

поле 4 (0x04 / 0x09) = частота в ГЦ     (наблюдалось 632, 7000)
поле 5 (0x05 / 0x0a) = Q × 10000        (0.7 -> 7000)
поля 1..3            = не декодированы
```

> **Важно:** в файле `Eq%401=|0|1262|0.7|0` — одна полоса, 4 поля.
> В HID — 5 полей на полосу. Соответствие не полное, это открытый вопрос.

> Дизайнеру: экран EQ теперь **можно** проектировать. Есть 4 полосы,
> у каждой тип/частота/Q/gain. **Но:** соответствие номеров типов
> фильтров названиям не проверено, полный маппинг полей HID↔файл
> не установлен, и диапазоны (min/max) для частоты, Q и gain не заданы
> явно. Рисовать слайдеры можно, но без подписанных границ.

### 2.4 Микшер — 10 каналов × 5 шин

**Статус на 2026-11-08:** адреса в HID **известны**, но канал **не отвечает**
ни на чтение, ни на запись. Доступен только через workspace-файл + MCC.

**Адреса из публичной документации:**

```
Target = микс + канал:  Mix A = 0x31/0x32, B = 0x33/0x34, C = 0x35/0x36 (L/R)
Property = ИСТОЧНИК:    01/02 = Playback 1/2, 03/04 = 3/4, 05/06 = 5/6,
                        07/08 = 7/8, 11/12 = Playback 9/10,
                        09/0a = IN, 0b/0c = AUX, 0d/0e = BT, 0f/10 = OTG
Value = Q25:            0 = mute, 2^25 = 33554432 = 0 dB, +12 dB = 133582600
```

**Проверено на нашем устройстве:** теги `0x31..0x36` в announce **не приходят**
(там только метры `0x3x:0x15`); запись по этой схеме в файл не попадает.

> Дизайнеру: **рисовать микшер пока рано** — канал не подтверждён.
> Если нужен экран, его придётся наполнять из workspace-файла.

**Обновлено 2026-11-08:** микшер **есть** в HID-протоколе, адреса известны
(`0x31..0x36`), но на нашем устройстве канал не отвечает. Практически
доступен только через workspace-файл.

**Каналы (10):** `IN12`, `AUX`, `BT`, `OTGIN`, `FX`, `PB12`, `PB34`,
`PB56`, `PB78`, `PB910`.

**Шины (5 в режиме Live):** `MixA`..`MixE`.
В Pro audio — 3 (`MixA`..`MixC`). В Mobile микшера нет.

**У каждого канала на каждую шину три параметра:**

| параметр | тип | пример |
|---|---|---|
| `Mix<X>_GAIN` | число | `12` |
| `Mix<X>_SOLO` | булево | `false` |
| `Mix<X>_MUTE` | булево | `false` |

Диапазон усиления в UI: **−90 .. +12**, шаг 1.

> Дизайнеру: это матрица «канал × шина» с тремя состояниями на клетку
> (gain, solo, mute). Каналов 10, шин 5 — 50 клеток. Число шин зависит
> от режима устройства.

### 2.6 Loopback и выходы

**Loopback (4 канала):** `LB12`, `LB34`, `LB56`, `LB78`.
У каждого: `AudioSource` (строка, например `FX`, `Mix A`), `GAIN`, `MUTE`.

**Выходы (2):** `HP` (наушники) и `OTGOUT`.
У каждого: `AudioSource` (например `Playback 1/2`), `GAIN`, `MUTE`.

> Дизайнеру: `AudioSource` — это **строка** с именем источника, а не число.
> Список допустимых значений не установлен — в файле встречались
> `FX`, `Mix A`, `Playback 1/2`.

## 3. События (что приходит от устройства)

Устройство присылает события **само**, без запроса:

| событие | когда приходит |
|---|---|
| состояние джека | при вставке/извлечении, а также в двух волнах после подписки |
| поворот ручки громкости | сразу, каждое движение |
| мьют выхода | в составе второй волны |
| состояние батареи | при изменениях |

**Следствия для интерфейса:**

- Значение может измениться **не по действию пользователя в браузере** —
  кто-то повернул ручку на самом устройстве.
- Значит нужна возможность показать «значение изменилось извне».
- После переподключения/пробуждения состояние может быть устаревшим.

## 4. Состояния и краевые случаи

| ситуация | что происходит |
|---|---|
| Устройство не подключено | HID-интерфейса нет, открыть нечего |
| Устройство подключено, подписки нет | молчит, событий не будет |
| Подписка истекла | поток событий прекращается без предупреждения |
| Кабель выдернут | записи начинают возвращать ошибки |
| Селектор не записан | состояние `Unknown`, реальное положение неизвестно |
| Значение не приходило ни разу | клиент не знает текущее значение |

**Ошибки записи, которые являются нормой при отключении:**
`ENODEV`, `ESHUTDOWN`, `EPROTO`, `EILSEQ`. Драйвер их не логирует как проблемы.

## 5. Что можно показывать по каждому параметру

Сводка типов данных, которые реально доступны:

| данные | доступность |
|---|---|
| целое значение параметра | да, для 7 громкостей |
| значение в дБ | вычисляется по кривой (см. §2.1) |
| выбранный источник | да, но только если клиент сам его записал |
| текущее положение ручки на устройстве | через события, а не чтением |
| состояние батареи | через события |
| состояние джека | через события |
| состояние мьюта | через события |
| уровень сигнала (метры) | **да**, шкала расшифрована: `dB = raw/10`, −90.2…0 dB |
| значения EQ (вкл/выкл, Gain) | **ДА**, из HID `0x9b:0x0f/0x10` и `0x91..0x94` (нужен handshake) |
| значения микшера (усиления, мьюты) | **нет** — канал не отвечает (см. §2.4) |
| уровни входов FX (5 шт.) | **да**, диапазон −90..+12, подтверждено живьём |
| редукция компрессора | **да**, `(comp13 − comp12)/10`, проверено |

### 5.1 Метры уровня — что известно точно

Наблюдаются на живом устройстве пассивным слушанием. Значения приходят
потоком, примерно раз в секунду, плюс чаще при изменении сигнала.

**Шкала расшифрована и проверена:**

```
дБ = raw / 10
```

| параметр | значение |
|---|---|
| диапазон шкалы | **−90.2 … 0 dB** |
| пол (тишина) | raw `−902` = **−90.2 dB** |
| ниже пола | не опускается никогда |
| единица | dB |

**Проверка:** наклон замерен на 8-дБ интервалах при высоком усилении —
10.25 / 10.00 / 9.88 raw на дБ. То есть ровно ×10.

**Три особых метра — НЕ метры:**

| адрес | поведение |
|---|---|
| `0x46:0x09` (`comp9`) | константа `−800`, не меняется |
| `0x46:0x0a` (`comp10`) | всегда `0`, канал не используется |
| `compressMeter` в окне COMP | всегда `0`, значения не отдаёт |

**Редукция компрессора** вычисляется как разница двух метров:

```
GR (dB) = (comp13 − comp12) / 10
```

где `comp12` = уровень ДО сжатия, `comp13` = ПОСЛЕ.
Проверено включением компрессора: при mic1=60 редукция −9.5 dB.

**Флаги для фронта** (отдаёт `GET /api/meters`):

| флаг | что значит | что рисовать |
|---|---|---|
| `atFloor: true` | метр на полу | «−∞» / тишина, НЕ «−90.2 dB» |
| `noData: true` | тег есть, значения нет | не показывать как 0 dB |
| `ageMs` | возраст значения | можно гасить «устаревший» |

**Уточнение по абсолютной шкале:** относительные величины (наклон, пол,
редукция) проверены и воспроизводимы. Привязка к абсолютному SPL
(что −66 dB — это именно −66 dB SPL) **не проверена** — эталонного
источника не было. Для индикации уровня этого достаточно.

**Что известно про ритм:** метры приходят сами, примерно раз в секунду,
и это основной поток данных от устройства (227 событий за ~8 секунд,
из них большинство — метры).

## 6. Ограничения, которые нельзя обойти

1. **Селекторы нельзя прочитать** — только записать и помнить.
2. **Некоторые параметры живут в файле, а не в устройстве.**
   Микшер, EQ, 48V, loopback читаются из workspace-файла MCC.
   Это значит: если менять настройки **с передней панели устройства**,
   файл может не обновиться, и клиент покажет устаревшее значение.
3. **Запись в файл вручную не применяется на лету** — MCC держит состояние
   в памяти. Применяется только при перезапуске MCC (~17 секунд на цикл).
4. **Пресеты частичные.** `Load preset` восстанавливает не всё состояние:
   проверено — из 6 параметров восстановились 2. Микшер, EQ, loopback,
   ducking в пресет не попадают.
5. **Компрессор: все 8 параметров пишутся, но требуют окна MCC.**
   Параметры: `Threshold`, `Ratio`, `Attack`, `Release`, `Gain`, `Mix`,
   плюс переключатели `Switch` и `GainAuto`.

   Запись идёт через отдельное окно `COMP` (открывается кнопкой `MORE`).
   Значения хранятся в workspace-файле, оттуда и читаются.

   **Что важно фронту:**
   - запись **пошаговая** — 1 шаг за нажатие, поэтому большие переходы
     занимают время (например `Release` 200 → 601 это 401 нажатие);
   - `Ratio` **нелинейный**: 1 … 4.0 шагом 0.1, дальше шаги растут
     (4.4, 4.7, 5.2 … 46.9), последняя позиция означает **∞**;
   - сервер возвращает `verified: true`, только если перечитал файл
     и подтвердил результат — на это можно опираться в UI;
   - запись **требует, чтобы окно `COMP` было на переднем плане**.
     Если пользователь переключится на другое приложение, сервер вернёт
     ошибку «окно COMP не в фокусе» вместо того, чтобы слать клавиши вслепую.

   Точные диапазоны и шкалы — `GET /api/compressor/scales`.
6. **Реверб не пишется через файл** — только кнопками в MCC.
   Но все 4 типа переключаются программно: `POST /api/reverb`.
7. **Диапазоны EQ измерены, но шкалы разные по типу.**
   - **Gain** — линейная, 1 дБ за шаг;
   - **Частота** — 100 шагов, `f(n) = 20·1000^(n/100)`, от 20 Гц до 20 кГц,
     шаг ≈ 119.6 центов (постоянный по логарифму);
   - **Q** — **линейной формулы нет**, только таблица из 46 значений,
     диапазон **0.1 … 15** (документация MCC врёт про минимум 0.707).
     Таблица отдаётся в `GET /api/eq/scales` — слайдер Q должен
     двигаться по индексам таблицы, а не по числу.

   Для ползунков: Gain и частоту можно рисовать обычным слайдером,
   Q — только дискретным, с 46 позициями.
8. **Типы EQ-фильтров перечислены, смена — только кликом мыши.**
   `Get /api/eq/types` отдаёт названия; `POST /api/eq/type` меняет тип,
   но реализация кликает реальной мышью (программный `Select()`
   возвращает успех и не применяет). Если окно EQ не на переднем
   плане — вернётся ошибка.
9. **Метры уровня — шкала расшифрована.**
   Все метры отдаются в дБ: `dB = raw / 10`, шкала **−90 … 0 dB**,
   пол `−90.2 dB`. Готовый эндпоинт — `GET /api/meters` (все уровни
   одним запросом) либо WebSocket-события с полем `meter.db`.

   **Что важно фронту:**
   - пол шкалы `−90 dB` — ниже метр не опускается вообще. Пришло
     `atFloor: true` — рисуйте «тишина/−∞», а не −90.2;
   - `noData: true` — тег есть, но значения не несёт (например `comp10`).
     Не показывайте как 0 dB, это не уровень;
   - `ageMs` — возраст значения. Если метры нужны «живыми», надо держать
     WebSocket: HTTP-запрос даёт снимок, который через 100 мс устарел;
   - обновление метров идёт **очень часто** (десятки раз в секунду на канал).
     Для индикаторов нужен троттлинг на клиенте, иначе браузер захлебнётся.

   **Редукция компрессора считается**: `GET /api/meters` отдаёт
   `gainReduction.db` = разница между уровнем после и до компрессора.
   Отрицательное значение = сжимает. Отдельный индикатор в HID **отсутствует**
   (бар в окне MCC всегда 0), поэтому гребёнку надо строить из этих чисел.

   ⚠️ Абсолютная калибровка в дБ SPL не проверялась — эталонного источника
   не было. Относительные величины (наклон, пол, редукция) стабильны.
10. **Никакой обратной связи по факту применения** — устройство не подтверждает
    запись. Оно либо принимает, либо нет, и отдельного ACK нет.
11. **Подписка требует постоянного продления** — браузер в фоне может душить
    таймеры, это надо учесть.
12. **Смена режима устройства перезагружает его** на 1–8 секунд —
    соединение пропадает, число шин микшера меняется (5 / 3 / 0),
    меняется и активный workspace-файл.
13. **Настройки устройства меняются быстро** — через HID, без MCC.
    Проверено: brightness, bluetooth, OTG power, USB-C power, auto power,
    типы кнопок — все пишутся напрямую (7/7).
14. **«Сброс к заводским» перезагружает устройство** и сбрасывает
    только его внутреннее состояние — workspace-файл остаётся как был.
    После сброса устройство ~8 секунд не отвечает, затем оживает
    после запуска M Control Center.
    **Для UI:** это необратимое действие, требующее подтверждения;
    после него нужно отдельно сбросить и файл.
