# M62 — микшер, loopback, ducking (расшифровано из USBPcap)

> Источник: захват трафика MCC при старте, 2026-11-08.
> Файл: `research/mixer-boot-capture.pcap` (28 МБ).
> Разбор: `src/tools/decode-mixer.py`.

---

## Главное: bulk push — это и есть запись микшера

Микшер **не пишется** отдельными кадрами. Он передаётся **пакетом**
между двумя кадрами-скобками:

```
0x11:0x20 = 1      открыть bulk push
   ... 242 кадра состояния за 485 мс ...
0x11:0x20 = 0      закрыть
0x11:0x26 = 1      запросить дамп обратно
```

**Вот почему перебор одиночными записями всегда давал тишину.** Устройство
не отдаёт кросспоинты ни в дампе состояния, ни эхом после записи. Оно их
только *принимает* — внутри брекета, пакетом, целиком.

Это же объясняет, почему нужен handshake: `0x11:0x01` открывает сессию,
в которой такой пакет вообще принимается.

## Структура матрицы микшера

```
группа (TT)  = один микс, L или R
свойство(PP) = один источник, L или R
значение     = Q25
```

| TT | микс | TT | микс |
|---|---|---|---|
| `0x31` | Mix A L | `0x32` | Mix A R |
| `0x33` | Mix B L | `0x34` | Mix B R |
| `0x35` | Mix C L | `0x36` | Mix C R |
| `0x37` | Mix D L | `0x38` | Mix D R |
| `0x3b` | Mix E L | `0x3c` | Mix E R |

Свойства `0x01..0x14` — 20 штук, это **10 стерео-источников × 2**:

```
0x01 / 0x02  источник 1 L / R
0x03 / 0x04  источник 2 L / R
0x05 / 0x06  источник 3 L / R
0x07 / 0x08  источник 4 L / R
0x09 / 0x0a  источник 5 L / R
0x0b / 0x0c  источник 6 L / R
0x0d / 0x0e  источник 7 L / R
0x0f / 0x10  источник 8 L / R
0x11 / 0x12  источник 9 L / R
0x13 / 0x14  источник 10 L / R
```

Нечётное свойство = левый канал, чётное = правый. Проверено: в группе
`0x33` сигнал в нечётных (`0x01..0x07`), в парной `0x34` — в чётных
(`0x02..0x08`). Это одно и то же стерео, разложенное по двум группам.

## Матрица по умолчанию (из захвата, в дБ)

```
        1   2   3   4   5   6   7   8   9   a   b   c   d   e   f  10  11  12  13  14
0x31  -inf -inf ...                                              (Mix A L, всё mute)
0x32  -inf -inf ...                                              (Mix A R, всё mute)
0x33   +0 -inf  +0 -inf  +0 -inf  +0 -inf  -6  -6  +0 -inf -inf -inf  +0 -inf  +0 -inf  +0 -inf
0x34  -inf  +0 -inf  +0 -inf  +0 -inf  +0  -6  -6 -inf  +0 -inf -inf -inf  +0 -inf  +0 -inf  +0
0x35  -inf ...                          -6  -6  +0 -inf -inf -inf  +0 -inf ...
0x36  -inf ...                          -6  -6 -inf  +0 -inf -inf -inf  +0 -inf ...
0x37  -inf ...                                                   (Mix D, всё mute)
0x38  -inf ...                                                   (Mix D, всё mute)
0x3b  -inf ...                                                   (Mix E, всё mute)
0x3c  -inf ...                                                   (Mix E, всё mute)
```

Сходится с workspace-INI:

| микс | `*_Visible` в INI | ненулевых в захвате |
|---|---|---|
| A | `@Invalid()` | 0 ✓ |
| B | 9 источников | 9 ✓ |
| C | `IN, AUX, BT` | 3 ✓ |
| D | `@Invalid()` | 0 ✓ |
| E | `@Invalid()` | 0 ✓ |

Источники 5 и 6 (`0x09/0x0a`, `0x0b/0x0c`) стоят на **−6 дБ** не случайно:
`16777216 = 2²⁴` — это ровно половина unity, то есть **−6.02 дБ**.
Такой дефолт у части источников.

Важно: `0x09` и `0x0a` ненулевые **в обеих** группах пары (`0x33` и `0x34`),
но это не «служебная ячейка» — это обычная пара L/R источника 5, у которой
оба канала стоят в −6 дБ.

**Проверка разметки по конфигу MCC** (`main.M62_Live`):

| микс | `*_Visible` | источников | ненулевых в захвате |
|---|---|---|---|
| B | IN, AUX, BT, FX, Playback 1/2…9/10 | **9** | **9** ✓ |
| C | IN, AUX, BT | **3** | **3** ✓ |

Совпадение точное — разметка пар подтверждена.

Порядок источников (какой номер = какой вход) **не подтверждён**: для этого
нужен захват с известным движением слайдера. Структура — 100%, порядок — нет.

## Ducking (0x43) — 7 параметров

Пишется в том же брекете, отдельным семейством:

```
0x43:0x01 = -30      порог, дБ
0x43:0x02 = 200      ?
0x43:0x03 = 16       ?
0x43:0x04 = 1000     ?
0x43:0x05 = 255      ?
0x43:0x06 = 255      ?
0x43:0x07 = 0        вкл/выкл
```

Сверка с секцией `[Ducking]` в INI — следующий шаг.

## Loopback (0x51..0x58) — 8 каналов

```
0x51:0x02 = 17       0x51:0x03 = 33554432
0x52:0x03 = 33554432
0x53:0x02 = 1        0x53:0x03 = 0
0x54:0x03 = 0
0x55:0x02 = 1        0x55:0x03 = 0
0x56:0x03 = 0
0x57:0x02 = 1        0x57:0x03 = 0
0x58:0x03 = 0
```

Похоже на 4 стерео-пары (LB12, LB34, LB56, LB78 в INI — тоже 4 секции):

```
0x51/0x52 = LB12    0x53/0x54 = LB34
0x55/0x56 = LB56    0x57/0x58 = LB78
```

свойство `0x02` = источник/вкл, `0x03` = gain Q25.

## Выходы и входы в том же брекете

```
0x21:0x02..0x05   вход IN1   (вкл, mute, gain, ?)
0x22:0x03..0x05   вход IN2
0x23:0x04..0x05   вход AUX
0x25:0x04..0x05   вход BT
0x27:0x04..0x05   вход OTG
0x61/0x63:0x03..0x04  OTG OUT  (gain, mute)
0x62/0x64:0x02..0x04  HP       (вкл, gain, mute)
```

Заметьте: `0x21:0x04 = 43` в захвате — это **ровно то значение**, которое
я записал в громкость IN1 в прошлом тесте. То есть MCC при старте
восстанавливает состояние из устройства, а не из своего файла.

## Обратное чтение

Из 242 адресов, которые MCC пишет в брекете, **в IN приходят только 3**.
Микшер в IN отсутствует полностью, кроме метров:

```
0x33:0x15  0x34:0x15  0x35:0x15  0x36:0x15   ← метры, не кросспоинты
0x39:0x01  0x39:0x02                        ← ?
```

**Практический вывод:** прочитать микшер из устройства нельзя. Источник
истины — либо собственная модель в нашей программе, либо workspace-INI.
Записывать можно — пакетом внутри брекета.

### Коды источников

**ЗАКРЫТО 2026-11-08.** Не выведено из последовательности, а взято из
mainline-патча `drivers/hid/hid-topping-m62.c` — таблицы `topping_sources[]`
и `topping_source_value[]`. Патч ровно на наше устройство
(`USB_VENDOR_ID_TOPPING 0x152a`, `USB_DEVICE_ID_TOPPING_M62 0x875c`),
таблица встречается в двух независимых копиях (v7-1 и lore-p2).

```
 0  Unknown          6  IN 1            12  Playback 1/2
 1  Mix A            7  IN 2            13  Playback 3/4
 2  Mix B            8  IN 1+2          14  Playback 5/6
 3  Mix C            9  AUX             15  Playback 7/8
 4  — ДЫРА          10  BT              16  Playback 9/10
 5  — ДЫРА          11  OTG IN          17  FX *
```

`*` — кода 17 в таблице драйвера нет. FX проверен нами вживую:
`0x51:0x02 = 17` при `Loopback_LB12.AudioSource = FX`.

**Все 16 кодов подтверждены на железе 2026-11-08** одним захватом
`research/source-codes.pcap`:

```

0x53:0x02 =  3   Mix C
0x55:0x02 =  8   IN 1+2
0x57:0x02 = 11   OTG IN
0x64:0x02 = 14   Playback 5/6
0x62:0x02 = 15   Playback 7/8

совпало: 6, расхождений: 0
```

### ⚠️ Дыра на 4 и 5 — исправление прежней ошибки

Раньше в `src/mixer-tags.js` стояли `mixD: 4` и `mixE: 5`. **Это неверно.**

Комментарий патча дословно:

> The same numbering serves the outputs and the loopback returns, and it
> has a hole where 4 and 5 would be, so the index of a control item is not
> the value the card wants and the two are kept side by side.

**Mix D и Mix E нельзя выбрать как источник.** Это не источники, а
**шины микшера** (`0x37/0x38` и `0x3b/0x3c`). На выход и в loopback
выбираются только `Mix A`, `Mix B`, `Mix C` — кодов 4 и 5 нет вообще.

Кроме того, `otgin` был `8`, а на самом деле **`11`**. Код `8` — это
`IN 1+2` (сумма двух входов), отдельный источник, которого у нас в
таблице не было.

## ЗАПИСЬ ПОДТВЕРЖДЕНА (2026-11-08)

Наш код формирует пакет, **идентичный MCC**. Проверено захватом:

```
1. РАЗМЕР
  200 = 200  OK

2. ПОРЯДОК АДРЕСОВ
  все 200 адресов совпадают по порядку  OK
```

### Точная вложенность циклов — ключ ко всему

Мой генератор расходился с MCC на 180 позициях из 200, пока не нашёлся
правильный порядок. Структура **тройная**:

```
для каждого БЛОКА свойств [09,0a], [0b,0c], [0f,10] ...
    для каждой ГРУППЫ 0x33, 0x34, 0x35 ... 0x31, 0x32
        для каждого свойства ВНУТРИ блока (2 штуки)
```

Первые 8 кадров эталона:

```
0x33:09  0x33:0a    0x34:09  0x34:0a
0x35:09  0x35:0a    0x36:09  0x36:0a
└ Mix B L ┘          └ Mix B R ┘          ...
```

Группа держится **два кадра подряд** (пара свойств блока), потом
следующая группа, и только пройдя все 10 групп — следующий блок.

**Две неверные гипотезы, которые я проверил и отбросил:**

| гипотеза | расхождений |
|---|---|
| группа за группой (0x31 целиком, потом 0x32) | 180 из 200 |
| свойство за свойством (0x33:09, 0x34:09, 0x35:09) | 180 из 200 |
| **блок → группа → свойство** | **0** |

Порядок групп тоже не по возрастанию: MCC начинает с `0x33` (Mix B),
и только потом `0x31`/`0x32` (Mix A).

### Готовый код

`src/mixer-tags.js`:

```js
import { buildMixerPacket, dbToQ25 } from './mixer-tags.js';

// состояние: шина -> источник -> дБ
const packet = buildMixerPacket({
  b: { pb12: -6, in1: -3 },
  c: { aux: -12 },
});

// отправка (внутри брекета bulk push)
send(0x11, PP_BULK_BEGIN, 1);
for (const f of packet) send(f.target, f.prop, f.value);
send(0x11, PP_BULK_BEGIN, 0);
send(0x11, PP_ANNOUNCE, 1);
```

### Почему проверка через INI не работала

MCC при старте берёт микшер **из своего workspace-INI**, а не из устройства.
Значит любую нашу запись он перезапишет своей матрицей, и по файлу
результат не увидеть. Проверять надо только сравнением пакетов.

## Что ПРОВЕРЕНО, а что нет

Честное разделение, чтобы не выдать гипотезу за факт.

### Проверено захватом

- Микшер передаётся **только** внутри брекета `0x11:0x20`.
- 10 групп × 20 свойств, все 200 кадров при старте MCC.
- Значения — Q25, `2²⁵` = 0 дБ, `2²⁴` = −6.02 дБ, `0` = mute.
- Независимые группы (A…E) попарно L/R.
- **Порядок источников** — какой номер свойства соответствует `IN 1`,
  `AUX`, `BT`, `Playback 1/2`. Три прогона с уникальными значениями
  в INI, третий закрыл карту (см. «ПОЛНАЯ КАРТА» выше).
- **Наша запись применяется.** `POST /api/mixer` → 200 кадров, пакеты
  побайтно совпали с тем, что шлёт MCC (`verify-our-write.py`, 200/200).
  Проверять по INI нельзя: MCC берёт микшер из своего файла.
- **Коды источников** — все 16, включая редкие (2026-11-08,
  `research/source-codes.pcap`, 6 из 6 совпало).
- Микшер **не читается обратно**: из 242 адресов в IN приходят только
  метры (`PP=0x15`), а не кросспоинты.

- **Питание входов (48V).** Через HID не найдено; живёт в INI
  (`[Input_IN1] 48V`).

---

## Практический вывод для нашей программы

Микшер — **write-only** канал. Поэтому:

- хранить состояние микшера **у себя** (своя модель);
- при подключении отправлять её пакетом;
- не пытаться прочитать из устройства;
- workspace-INI может служить источником начального состояния, но
  только если MCC закрыт (иначе он перезапишет файл своей памятью).

Это же касается ducking и loopback.
