## Что решаем

Сейчас бекенд работает, но **четверть маршрутов требует запущенного
окна M Control Center**. Это значит: чтобы поправить EQ или компрессор,
пользователь обязан держать открытым 20-мегабайтное Qt-приложение —
то есть замена MCC не выполняет свою задачу.

Цель: довести до состояния, когда MCC не нужен ни запущенным, ни
(в идеале) установленным.

**Не входит в план:** прошивка устройства (отдельный трек, высокий риск),
раскрытие протокола вендором (отказал), поддержка других ОС.

### Точные цифры автономности

Измерено двумя инструментами; цифры ниже — по фактическим вызовам
(`node src/tools/autonomy-audit.js`), он точнее.

| класс | маршрутов | что значит |
|---|---|---|
| чистый HID | **30 из 56 (54%)** | MCC не нужен вообще |
| нужны файлы MCC | 9 из 56 (16%) | нужна установка, процесс — нет |
| управляет процессом MCC | 1 из 56 (2%) | смена режима: останавливает и запускает |
| **нужен запущенный MCC** | **16 из 56 (29%)** | падает без открытого окна |

Две прежние оценки были неверны: `autonomy-report.js` давал 61%/80%,
но он ищет подстроки-маркеры и промахивается — ждёт `'compressor.open'`,
а код вызывает `comp.openCompWindow()`, поэтому открытие окна
компрессора попадало в «чистый HID». Новая цифра хуже, но правдивее.

**Почему 16, а не 11.** Раньше считалось, что хватает исправить
запись. На деле от окна MCC зависят и **чтения**:
`readEqSwitch()` вызывает `ensureMcc()`, `readEqTypes()` читает
значения из открытого попапа, `readCompressorValues()` читает
workspace-INI. Поэтому переделка записи на HID снимает зависимость
не у всех маршрутов.

## 1. Первый приоритет: открыть, пишется ли EQ напрямую через HID

Прежде чем что-то переписывать, нужно закрыть противоречие в записях.

### 1.1 Противоречие, которое надо снять

Два замера не согласуются:

| источник | что говорит | чем получен |
|---|---|---|
| `research/NOTES.md` §123 | EQ пишется напрямую, **8 из 8** | `verify-eq-comp-writes.js`, **снимок 7 с** |
| `research/NOTES.md` §134.8 | напрямую не пишется, только в брекете | `eq-write-strategies.js` |

**Оба замера сомнительны.** §123 использовал `SNAPSHOT_MS = 7000`,
а по §130 в Prof-режиме блоки `0x91` приходят на 18.8 с — то есть
снимок был короче, чем нужно, и «принято» могло быть артефактом.
Замер §134.8 делался в Live-режиме, который сам по себе другой.

**Отсюда правило:** ни одну из двух цифр нельзя принимать на веру.

### 1.2 Единственный опыт, который решает вопрос

Условия — все обязательны, иначе результат снова ничего не докажет:

```
Режим:      Prof  (проверить через node src/tools/state-check.js)
MCC:        ЗАКРЫТ ПОЛНОСТЬЮ, не в трее
Окно дампа: 26 секунд (блоки 0x91 приходят на 18-19 с)
Чтение:     в НОВОЙ сессии (переподключение сбрасывает кэш)
Наушники:   отключены, или MUTE (проверяется safety-check.js)
```

Последовательность (скрипт `src/tools/eq-write-definitive.js` уже так умеет):

1. Снимок «до» — 26 с, свежая сессия. Убедиться, что `0x91:0x03` **есть**
   в снимке. Если тега нет — стоп, метод негоден, см. п. 1.3.
2. Записать `0x91:0x03 = 3` **одиночным кадром**, без брекета.
3. Закрыть соединение.
4. Снимок «после» — 26 с, свежая сессия.
5. Если стало 3 → прямой путь работает, брекет не нужен.
   Если осталось 0 → повторить с брекетом (`eq-write-strategies.js`,
   стратегия B — она уже дала «принято»).
6. Вернуть исходное значение тем же способом, которым оно применилось.

**Критерий готовности:** значение изменилось и сохранилось после
переподключения. Не «UI показывает», а «тег в свежем дампе другой».

### 1.3 Обязательный контрольный опыт

Если `0x91` не пришёл в снимке «до» — **это не отказ записи**,
а сбой метода. Проверить `node src/tools/control-eq-arrival.js`:
он делает два снимка подряд **без всякой записи**.

- Оба снимка содержат `0x91` → метод годен, можно делать выводы.
- Второй снимок пуст → MCC держит HID-поток или снимок короток.
  Вывод о записи делать **нельзя**.

Это правило уже спасло от ложного вывода один раз (§130).

### 1.4 Что делать по результату

| результат | действие |
|---|---|
| прямой путь работает | переписать `setEqParamTo`/`nudgeEqParam` на `transport.send`. Проще некуда: один вызов вместо кликов |
| работает только брекет | добавить в `transport.js` метод `writeEqInBracket()`, по образцу `writeMixer()` |
| **не работает ни то, ни другое** | **зафиксировать в NOTES.md с указанием условий опыта. Оставить UI-путь. Перейти к §2 (фронтенд)** |

Третий исход — не провал дня. Это закрытый вопрос: тогда UI-путь
единственный, и это надо записать как факт, а не как догадку.

### 1.5 Что проверить после успеха

Одного поля полосы недостаточно. Поля полосы (проверить раскладку):

```
0x01 / 0x06 = вкл-выкл        0/1
0x02 / 0x07 = тип фильтра     1 = peaking
0x03 / 0x08 = gain, дБ
0x04 / 0x09 = частота, Гц
0x05 / 0x0a = Q x 10000
```

Полоса 1 это `0x01..0x05`, полоса 2 это `0x06..0x0a`. Блоки `0x91/0x92`
— канал 1, `0x93/0x94` — канал 2. Итого 4 блока x 2 полосы x 5 полей
= **40 параметров**.

Проверять не все 40, а по одному полю каждого типа (вкл, тип, gain,
частота, Q) = 5 опытов, плюс один на второй канал. Если раскладка
подтвердится на них — остальное следует из структуры.

### 1.6 Компрессор — тот же вопрос

§123 утверждает, что компрессор пишется напрямую 8/8, но с тем же
коротким снимком. Проверить тем же способом: одно поле (`0x46:0x04`,
Attack), свежая сессия, дамп с окном достаточной длины.
Блок `0x46` приходит раньше `0x91`, но окно всё равно нужно не меньше
15 с, чтобы увидеть его в свежем дампе стабильно.

## 2. Реверб: сначала карта, потом запись

### 2.1 Проблема

`docs/EFFECTS.md` называет семейство `0x44` блоком шумоподавления.
Формально это верно для `0x44:06/07/09` (NC), но `0x44` несёт больше:

- `0x44:01..05` — уровни FX-входов (IN1, IN2, AUX, BT, OTG)
- `0x44:0d/0e` — **метры FX in/out**, есть только в Live
- `0x44:06/07/09` — шумоподавление
- `0x44:08/0a/0b/0f` — **не расшифрованы**

Именно на `0x44:0d/0e` держится определение режима Live в
`src/modes.js`, так что это точно не только NC.

**Ни одного тега реверба мы пока не знаем.** Реверб — отдельный
объект UI: `Effect_Reverb` с кнопками Studio/Live/Hall и дилами
Room, Width, Decay.

### 2.2 Что делать

Не писать, а **сначала составить карту**. Метод уже применялся для NC
(`docs/EFFECTS.md`): снимок `0x44` → движение одного дила в UI →
снимок заново → сравнение.

Порядок:

1. Режим Live. MCC закрыт.
2. Снимок `0x44` (записать все значения).
3. Запустить MCC, двинуть `dialRoom` на несколько шагов, закрыть MCC.
4. Снимок заново. Какой тег изменился → это Room.
5. Повторить для Width и Decay.
6. Переключить тип реверба (Studio → Live) → найти тег типа.

**Критерий готовности:** для каждого из четырёх параметров реверба
известен конкретный адрес `0x44:PP`.

### 2.3 Потом — проверить запись

Только когда адреса известны, имеет смысл проверять запись. Тем же
протоколом из §1.2. Если не пишется — зафиксировать и оставить UI-путь.

## 3. Отвязаться от установленного MCC

Сейчас 9 маршрутов требуют папки
`C:\Program Files\TOPPING Pro\M Control Center\Workspace\M62`.

### 3.1 Что уже есть

**Не надо писать новое хранилище.** `src/snapshots.js` — это уже
полный снимок состояния: `captureSnapshot()` собирает и HID-кеш,
и секции workspace (inputs, mixer, eq, loopback, outputs, ducking,
effects, compressor) в один JSON. Есть `listSnapshots`, `getSnapshot`,
`diffSnapshots`, `applySnapshot()`.

### 3.2 Решение

**Одна модель состояния, один файл, один писатель.**

- `snapshots.js` становится рабочим хранилищем, а не диагностическим
  дампом: его каталог переезжает в `%APPDATA%\m62\`.
- На старте — однократный импорт из INI MCC, если он установлен
  (для миграции). Дальше INI не читается.
- Микшер и loopback из устройства не читаются вообще (проверено:
  `IN=0` во всех захватах), поэтому своя модель — не костыль,
  а единственный способ знать их состояние.

**Отвергнутая альтернатива:** оставить INI источником истины и
сделать только импортёр. Отвергнуто потому, что микшер и loopback
нельзя прочитать из устройства — значит INI нельзя ни проверить,
ни восстановить при расхождении.

### 3.3 Что будет с `POST /api/workspace/apply`

Сейчас он правит INI и перезапускает MCC (~17 с). После перехода
на своё хранилище он либо перестаёт существовать, либо становится
«применить снимок», без MCC.

## 4. Фронтенд

Не начат. Документация готова: [`FOR-DESIGNER.md`](FOR-DESIGNER.md),
[`API.md`](API.md).

**Порядок экранов:**

1. Громкости и настройки — чистый HID, работает всегда.
2. Микшер — не читается из устройства, брать из модели (§3).
3. EQ — после того как решён §1.

**Что учесть:**

- Режим меняет состав экранов: Live — микшер и loopback, Mobile — ни
  того ни другого, Prof — EQ наушников, но без эффектов. Экраны
  перестраиваются по режиму.
- Пока маршрут требует MCC, UI должен показывать «недоступно», а не
  молча падать.
- Запись применяется отложенно. Оптимистичное обновление корректно,
  но нужен способ заметить «запись не доехала»: повторное чтение
  через N секунд и расхождение → показать пользователю.
- Метры: 22 штуки, `dB = raw / 10`, пол `-90.2 dB`.

**Критерий готовности первой итерации:** экран громкостей, который
показывает и меняет 7 громкостей и 2 селектора при закрытом MCC.

## 5. Прошивка — отдельный трек, не сейчас

Контейнер 1188 КБ не распакован. Внутри STM32G070R (Cortex-M0+) + DSP01.

**Зачем:** понять, можно ли добавить функции, которых нет в текущей
прошивке. Например «суммарный режим» (все три режима одновременно) —
это вопрос создания блоков в прошивке, а не ограничение железа.

**Условие входа, которого сейчас нет:** нужен способ восстановления
при ошибке — рабочий дамп прошивки и проверенный путь DFU. Пока их нет,
начинать нельзя: ошибка превращает устройство в кирпич.

Пока условие не выполнено — трек закрыт.

## 7. Протокол опыта — применять к §1 и §2

Три раза проект получал ложные выводы из-за метода. Перед каждым
опытом фиксировать:

```
режим:        Prof / Live / Mobile  (node src/tools/state-check.js)
MCC:          закрыт полностью, не в трее
окно дампа:   26 с (Prof), 15 с минимум для 0x46
чтение:       в новой сессии, не в той же
наушники:     отключены или MUTE (src/tools/safety-check.js)
```

Правила:

1. **Работающий MCC откатывает записи.** Замерено: с MCC запись
   `0x46:02 = -28` не применялась 60+ секунд, без MCC — 10 секунд.
2. **Чтение в той же сессии показывает кэш.** Нужно переподключение.
3. **`undefined` после записи = НЕ УВИДЕЛИ, а не ОТКАЗАНО.**
   Любой отрицательный результат требует контрольного опыта, где
   то же самое измеряется БЕЗ записи.
4. **Логика не должна дублироваться.** `state-check.js` имел свою копию
   определения режима, разошёлся с `modes.js` и врал на живом
   устройстве. Одна логика — один модуль.

**После каждого опыта:** вернуть изменённые значения, проверить
переподключением, записать в `research/NOTES.md` условия и результат.
