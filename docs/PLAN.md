## Что решаем

Сейчас бекенд работает, но **четверть маршрутов требует запущенного
окна M Control Center**. Это значит: чтобы поправить EQ или компрессор,
пользователь обязан держать открытым 20-мегабайтное Qt-приложение —
то есть замена MCC не выполняет свою задачу.

Цель: довести до состояния, когда MCC не нужен ни запущенным, ни
(в идеале) установленным.

**Не входит в план:** прошивка устройства (отдельный трек, высокий риск),
раскрытие протокола вендором (отказал), поддержка других ОС.

## 1. ДОСТИГНУТО: EQ и компрессор через HID

**Закрыто 2026-11-10.** Оба вопроса решены, код переписан,
маршруты больше не требуют MCC.

### 1.1 Ответ на противоречие

Противоречие между §123 и §134.8 снято. **Оба замера были неверны**,
и причина одна:

> Устройство отдаёт блоки `0x91..0x94` (EQ входов) **только на первый
> ANNOUNCE в сессии**. Повторный announce в той же сессии EQ не
> возвращает.

Замерено:

```
одна сессия, announce #1:  101 тег, EQ=39
одна сессия, announce #2:   46 тегов, EQ=0
одна сессия, announce #3:   47 тегов, EQ=0
НОВАЯ сессия, announce #1:  97 тегов, EQ=40
```

Значит «снимок до / снимок после» в ОДНОЙ сессии не работает никогда.
Все инструменты, которые так делали, давали ложный отрицательный
результат — и §123 (снимок 7 с), и §134.8.

**Правило:** после записи нужна НОВАЯ сессия.

### 1.2 Что проверено на живом устройстве

MCC закрыт, чтение в новой сессии, каждая запись откатывалась.

EQ входов, все пять полей полосы — **7 из 7**:

```
вкл полосы 1       0x91:01    0 -> 1        принято
тип полосы 1       0x91:02    1 -> 2        принято
gain полосы 1      0x91:03    0 -> 3        принято
частота полосы 1   0x91:04  632 -> 1000     принято
Q полосы 1         0x91:05 7000 -> 10000    принято
gain полосы 2      0x91:08    0 -> 2        принято
gain канала 2      0x93:03    0 -> 2        принято
```

Общий включатель EQ: `0x9b:0f` 0 → 1, принято.

Компрессор — **5 из 5**:

```
Threshold  0x46:02  -28 -> -20    принято
Ratio      0x46:03   40 -> 60     принято
Attack     0x46:04    5 -> 10     принято
Release    0x46:05  200 -> 300    принято
Mix        0x46:08  100 -> 90     принято
```

Брекет `0x11:0x20` для этого НЕ нужен — одиночные кадры работают.
(Для микшера нужен.)

### 1.3 Что сделано в коде

Новые модули:

- `src/eq-hid.js` — раскладка EQ (4 блока × 2 полосы × 5 полей = 40
  параметров), адресация, чтение, валидация
- `src/comp-hid.js` — параметры компрессора, масштаб Ratio ×10

В `src/transport.js`: `writeFrames()` (одиночные кадры) и `writeBulk()`
(в брекете, для микшера).

Переведены с UIAutomation на HID: `POST /api/eq/band`,
`/api/eq/band/enable`, `/api/eq/type`, `/api/eq/switch`,
`/api/compressor/param`, `/api/compressor/switch`, `GET /api/eq`,
`/api/eq/types`, `/api/eq/dials`, `/api/compressor`.

### 1.4 Ловушка, найденная по ходу: коды типов фильтров

Массив в UI нумеруется с нуля, устройство — с единицы:

```
filterTypes = ['peaking','lowpass','highpass','lowshelf','highshelf']
                   0          1         2          3          4

устройство:  peaking=1  lowpass=2  highpass=3  lowshelf=4  highshelf=5
```

Отправка индекса массива превращала `peaking` в `0`, и полоса теряла
тип. Устройство принимало `0` без ошибки. Обнаружено при чтении свежего
снимка. Исправлено таблицей `DEVICE_TYPE_CODE`.

## 2. Реверб: сначала карта, потом запись

Остался единственный блок эффектов, где мы не знаем адресов.

### 2.1 Проблема

`docs/EFFECTS.md` называет семейство `0x44` блоком шумоподавления.
Формально это верно для `0x44:06/07/09` (NC), но `0x44` несёт больше:

- `0x44:01..05` — уровни FX-входов (IN1, IN2, AUX, BT, OTG)
- `0x44:0d/0e` — **метры FX in/out**, есть только в Live
- `0x44:06/07/09` — шумоподавление
- `0x44:08/0a/0b/0f` — **не расшифрованы**

Именно на `0x44:0d/0e` держится определение режима Live в
`src/modes.js`, так что это точно не только NC.

**Ни одного тега реверба мы пока не знаем.** Реверб — отдельный
объект UI: `Effect_Reverb` с кнопками Studio/Live/Hall и дилами
Room, Width, Decay.

### 2.2 Что делать

Не писать, а **сначала составить карту**. Метод уже применялся для NC
(`docs/EFFECTS.md`): снимок `0x44` → движение одного дила в UI →
снимок заново → сравнение.

Порядок:

1. Режим Live. MCC закрыт.
2. Снимок `0x44` (записать все значения).
3. Запустить MCC, двинуть `dialRoom` на несколько шагов, закрыть MCC.
4. Снимок заново. Какой тег изменился → это Room.
5. Повторить для Width и Decay.
6. Переключить тип реверба (Studio → Live) → найти тег типа.

**Критерий готовности:** для каждого из четырёх параметров реверба
известен конкретный адрес `0x44:PP`.

### 2.3 Потом — проверить запись

Только когда адреса известны, имеет смысл проверять запись. Тем же
протоколом из §1.2. Если не пишется — зафиксировать и оставить UI-путь.

## 3. Отвязаться от установленного MCC

Сейчас 9 маршрутов требуют папки
`C:\Program Files\TOPPING Pro\M Control Center\Workspace\M62`.

### 3.1 Что уже есть

**Не надо писать новое хранилище.** `src/snapshots.js` — это уже
полный снимок состояния: `captureSnapshot()` собирает и HID-кеш,
и секции workspace (inputs, mixer, eq, loopback, outputs, ducking,
effects, compressor) в один JSON. Есть `listSnapshots`, `getSnapshot`,
`diffSnapshots`, `applySnapshot()`.

### 3.2 Решение

**Одна модель состояния, один файл, один писатель.**

- `snapshots.js` становится рабочим хранилищем, а не диагностическим
  дампом: его каталог переезжает в `%APPDATA%\m62\`.
- На старте — однократный импорт из INI MCC, если он установлен
  (для миграции). Дальше INI не читается.
- Микшер и loopback из устройства не читаются вообще (проверено:
  `IN=0` во всех захватах), поэтому своя модель — не костыль,
  а единственный способ знать их состояние.

**Отвергнутая альтернатива:** оставить INI источником истины и
сделать только импортёр. Отвергнуто потому, что микшер и loopback
нельзя прочитать из устройства — значит INI нельзя ни проверить,
ни восстановить при расхождении.

### 3.3 Что будет с `POST /api/workspace/apply`

Сейчас он правит INI и перезапускает MCC (~17 с). После перехода
на своё хранилище он либо перестаёт существовать, либо становится
«применить снимок», без MCC.

## 4. Фронтенд

Не начат. Документация готова: [`FOR-DESIGNER.md`](FOR-DESIGNER.md),
[`API.md`](API.md).

**Порядок экранов:**

1. Громкости и настройки — чистый HID, работает всегда.
2. Микшер — не читается из устройства, брать из модели (§3).
3. EQ — **готово**, работает через HID (§1).
4. Эффекты — последними, там больше всего неизвестного.

**Что учесть:**

- Режим меняет состав экранов: Live — микшер и loopback, Mobile — ни
  того ни другого, Prof — EQ наушников, но без эффектов. Экраны
  перестраиваются по режиму.
- Пока маршрут требует MCC, UI должен показывать «недоступно», а не
  молча падать.
- Запись применяется отложенно. Оптимистичное обновление корректно,
  но нужен способ заметить «запись не доехала»: повторное чтение
  через N секунд и расхождение → показать пользователю.
- Метры: 22 штуки, `dB = raw / 10`, пол `-90.2 dB`.

**Критерий готовности первой итерации:** экран громкостей, который
показывает и меняет 7 громкостей и 2 селектора при закрытом MCC.

## 7. Протокол опыта — применять к §2 и §3

Четыре раза проект получал ложные выводы из-за метода. Перед каждым
опытом фиксировать:

```
режим:        Prof / Live / Mobile  (node src/tools/state-check.js)
MCC:          закрыт полностью, не в трее
окно дампа:   18-20 с (блоки 0x91 приходят на 2-3 с, но дамп
              должен успеть собраться целиком)
чтение:       в НОВОЙ сессии, не в той же  ← главное
наушники:     отключены или MUTE (src/tools/safety-check.js)
```

Правила:

1. **EQ приходит только на первый ANNOUNCE сессии.** Повторный
   announce в той же сессии блоки `0x91..0x94` НЕ возвращает
   (проверено: 101 тег на первом, 46 на втором). Поэтому «снимок до /
   снимок после» в одной сессии не работает никогда — второй снимок
   пуст, и это легко принять за отказ устройства.
2. **Работающий MCC откатывает записи.** Замерено: с MCC запись
   `0x46:02 = -28` не применялась 60+ секунд, без MCC — 10 секунд.
3. **`undefined` после записи = НЕ УВИДЕЛИ, а не ОТКАЗАНО.**
   Любой отрицательный результат требует контрольного опыта, где
   то же самое измеряется БЕЗ записи.
4. **Не выводить код устройства из индекса массива UI.** Типы
   фильтров в UI нумеруются с нуля, в устройстве — с единицы.
   На этом уже была ошибка.
5. **Логика не должна дублироваться.** `state-check.js` имел свою копию
   определения режима, разошёлся с `modes.js` и врал на живом
   устройстве. Одна логика — один модуль.

**После каждого опыта:** вернуть изменённые значения, проверить
переподключением, записать в `research/NOTES.md` условия и результат.
