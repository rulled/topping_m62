## 1. Главное на завтра: снять зависимость от UI MCC

Это самый большой оставшийся резерв, и он не про реверс — про код.
Протокол уже умеет всё нужное, сервер просто ходит не тем путём.

### 1.1 Перевести EQ входов с UI на HID

**Что известно.** Запись `send(0x91, 0x03, v)` напрямую НЕ применяется,
но ПРИМЕНЯЕТСЯ внутри брекета:

```
0x11:0x20 = 1
0x91:0x03 = 3
0x11:0x20 = 0
0x11:0x26 = 1
```

Замер (`eq-write-strategies.js`):

```
A. одиночная запись           -> не принято
B. внутри брекета 0x11:0x20   -> ПРИНЯТО (0 -> 3)
C. запись + 0x11:0x05 (save)  -> прервано ошибкой записи
```

**Что сделать:**

1. Повторить опыт B на чистом устройстве (MCC закрыт ПОЛНОСТЬЮ,
   не в трее) — в прошлый раз был Live-режим, а тест писал в `0x91`.
2. Проверить все пять полей полосы: вкл, тип, gain, freq, Q,
   а не только gain.
3. Проверить обе полосы каждого из четырёх блоков (`0x91..0x94`).
4. Если подтвердится — переписать `src/eq-control.js`:
   `setEqParamTo` / `nudgeEqParam` должны слать кадры, а не нажимать
   клавиши в окне. Убрать `isEqWindowOpen` из пути записи.
5. Перепроверить `/api/eq/band`, `/api/eq/type`, `/api/eq/switch`,
   `/api/eq/band/enable` — они перестанут требовать окно EQ.

**Выигрыш:** 4 маршрута из 11 перестанут требовать запущенного MCC.
Плюс отпадает странность «окно EQ закрыто — сначала POST /api/eq/open».

### 1.2 Перевести компрессор с UI на HID

**Что известно.** §123 в NOTES.md утверждает, что компрессор пишется
через HID (8/8: Attack, Release, Mix). Но `comp-control.js` двигает
дилы клавишами (`pressCompDial`).

Вероятно, та же история, что с EQ: нужен брекет. Проверить.

**Что сделать:**

1. Проверить запись `0x46:0x02..0x08` внутри брекета, с переподключением.
2. Если работает — переписать `setCompressorParam` на прямые кадры.
3. Убрать `POST /api/compressor/open` / `close` из обязательного пути.

**Выигрыш:** 2 маршрута (всего станет 5 из 11).

### 1.3 Реверб: выяснить, пишется ли вообще

**Что известно.** Теги `0x44:0x08..0x0f` читаются. Запись «только
относительными шагами через UI» — это описание текущей реализации,
а не доказанное свойство железа.

В Prof-режиме блоков `0x44` нет вообще, поэтому там проверить нельзя.
Нужен Live или Mobile.

**Что сделать:** попробовать запись `0x44:0x0b` (тип реверба) одиночным
кадром и в брекете, в Live-режиме, при закрытом MCC, с переподключением.

**Выигрыш:** 2 маршрута. Если не пишется — честно зафиксировать
и оставить UI-путь как единственный.

### 1.4 Итог по этому блоку

Если 1.1–1.3 удадутся, автономность станет:

```
было:  61% без MCC, 80% без запущенного
стало: ~80% без MCC, 100% без запущенного
```

Тогда MCC нужен только для чтения/записи своих INI-файлов
(11 маршрутов), а запущенным — не нужен вообще.

## 2. Отвязаться от установленного MCC

Сейчас путь зашит: `C:\Program Files\TOPPING Pro\M Control Center\Workspace\M62`.
Если MCC удалить — 11 маршрутов умрут.

**Варианты:**

- **Своё хранилище.** Микшер и loopback не читаются из устройства
  вообще, значит своя модель состояния — не костыль, а необходимость.
  Держать JSON в `%APPDATA%\m62\` и не зависеть от INI.
- **Экспорт/импорт.** Уметь читать INI MCC (для миграции), но не
  требовать его наличия.

Это же решит проблему «микшер не читается обратно»: своё состояние
всегда полное, не нужно угадывать.

## 3. Фронтенд

Не начат вообще. Документация для него готова —
[`docs/FOR-DESIGNER.md`](../docs/FOR-DESIGNER.md) и
[`docs/API.md`](../docs/API.md).

**Что важно знать перед началом:**

- Три канала данных (HID / файл / UI MCC) — фронт не должен знать,
  откуда пришло значение, но должен уметь показать «недоступно»
  для того, что требует MCC.
- Режим устройства меняет состав экранов: в Live есть микшер и
  loopback, в Mobile нет, в Prof есть EQ наушников но нет эффектов.
  Экраны должны перестраиваться.
- Микшер не читается из устройства — фронт получает его из своей
  модели или из файла.
- Запись применяется отложенно: не ждать ACK, оптимистичное
  обновление экрана корректно.
- Метры приходят потоком, 22 штуки, шкала `dB = raw / 10`,
  пол `-90.2 dB`.

**Порядок:** сначала экран громкостей и настроек (чистый HID, работает
всегда), потом микшер, потом EQ, эффекты последними.

## 4. Прошивка (не начата, 10%)

Контейнер 1188 КБ не распакован. Внутри STM32G070R (Cortex-M0+) + DSP01.

**Зачем это вообще:** понять, можно ли добавить функции, которых нет
в текущей прошивке. Например, тот самый «суммарный режим всех трёх»,
о котором спрашивал DEISU, — это не ограничение железа, а вопрос
создания блоков в прошивке.

**Что нужно:** Ghidra с ARM Cortex-M. Xtensa не применим.

**Риск:** высокий. Прошивка устройства — это кирпич при ошибке.
Начинать только когда есть чем восстанавливать (DFU-режим, дамп
рабочей прошивки).

## 5. Мелкие открытые вопросы

| вопрос | статус |
|---|---|
| 48V (фантом) через HID | **не отдаётся.** У входа IN1 приходят только 3 свойства: метр, громкость, джек. Управляется только через INI |
| Expander (`Expander_IN1/IN2`) | есть в строках MCC, в UI и дампах не встречались. Вероятно, не реализовано |
| `0x44:0x08/0x0a/0x0b/0x0f` | сущности не до конца расшифрованы (room, decay, width) |
| `0x9b:0x12/0x13` | «param 2» EQ — смысл не установлен |
| Порядок инициализации | нужно ли что-то кроме handshake для полного дампа во всех режимах |

## 7. Правила, выведенные из ошибок

Три раза проект получал ложные выводы из-за метода. Записываю, чтобы
не повторять:

1. **Работающий MCC откатывает записи.** Замерено: с MCC запись
   не применялась 60+ секунд, без MCC — 10 секунд.
2. **Чтение в той же сессии показывает кэш.** Нужно переподключение.
3. **`undefined` после записи = НЕ УВИДЕЛИ, а не ОТКАЗАНО.**
   Любой отрицательный результат требует контрольного опыта, где
   то же самое измеряется БЕЗ записи.

И четвёртое, найденное сегодня: **логика не должна дублироваться**.
`state-check.js` имел свою копию определения режима, разошёлся с
`modes.js` и врал на живом устройстве, показывая Mobile при Live.
