# M62 Web Client — Protocol Reference

Проверено на firmware `V87.05.45.48.27`, `bcdDevice 3.27`.
Источник: mainline-драйвер `hid-topping` (Mikhail Gavrilov) + собственный
реверс `M Control Center.exe` + живая проверка устройства.

---

## 1. Транспорт

| параметр | значение |
|---|---|
| VID / PID | `0x152A` / `0x875C` |
| Interface | **4** (`mi_04`) — vendor control channel |
| Interface 3 | Application Specific / DFU — **никогда не трогать** |
| Класс | HID, `UsagePage 0x0001`, `Usage 0x0000` |
| Product string | `M62` |
| Manufacturer string | `Topping` |

Путь устройства (Windows):
```
\\?\hid#vid_152a&pid_875c&rev_0248&mi_04#<instance>#{4d1e55b2-f16f-11cf-88cb-001111000030}
```
GUID `{4d1e55b2-f16f-11cf-88cb-001111000030}` — стандартный HID class GUID.

### Размеры отчётов

| поле | значение | смысл |
|---|---|---|
| `InputReportByteLength` | **17** | 1 report ID + 16 |
| `OutputReportByteLength` | **17** | 1 report ID + 16 |
| `FeatureReportByteLength` | **0** | фича-отчётов НЕТ |

### Что не работает

- **Control pipe мёртв.** `GET_REPORT` и `SET_REPORT` возвращают `EPIPE` для
  всех типов отчётов. Причина видна из `FeatureReportByteLength = 0`.
- **Feature reports недоступны вообще.**

Единственный путь — **interrupt IN / OUT endpoints** через `WriteFile` /
`ReadFile` (Windows HID API).

## 2. Формат кадра

### Что отправляем (15 байт)

```
+0   22 33           magic
+2   20 01 01        фиксированный заголовок
+5   TT              target
+6   PP              property
+7   s32             значение, BIG-ENDIAN
+11  u16             CRC-16/MODBUS по байтам 2..10, BIG-ENDIAN
+13  66 77           magic
```

**Итого: 15 байт.** При отправке через Windows HID API спереди добавляется
байт report ID (`0x00`), потому что `OutputReportByteLength = 17`.

```
00 | 22 33 20 01 01 TT PP v v v v c c 66 77
^report ID
```

### Что принимаем (17 байт)

```
00 | 22 33 20 01 01 TT PP v v v v c c 66 77 XX
^report ID                                    ^pad
```

Кадр устройства — те же 15 байт **плюс один байт паддинга**. Плюс report ID
от HID-слоя = 17.

Холостой опрос возвращает **16 нулей**.

### CRC-16/MODBUS

| параметр | значение |
|---|---|
| алгоритм | CRC-16/MODBUS |
| полином | `0xA001` (отражённый `0x8005`) |
| init | `0xFFFF` |
| refin / refout | true / true |
| xorout | `0x0000` |
| покрытие | байты **2..10** включительно (9 байт) |
| порядок в кадре | старший байт первым (BE) |

**ВАЖНО:** вендорское приложение посылает `00 00` вместо CRC, и устройство
это **принимает**. То есть **прошивка не проверяет CRC входящих кадров.**
Свой клиент обязан считать CRC корректно (для совместимости), но при отладке
можно слать нули.

## 3. Жизненный цикл соединения

### 3.0 SESSION HANDSHAKE — ОБЯЗАТЕЛЕН ПЕРВЫМ

```
TT = 0x11, PP = 0x01, value = 1
```

Устройство отвечает `0x11/0x01 = 2` (в публичной документации для другой
прошивки — `3`). **Это не ACK ради вежливости: без handshake карта отдаёт
не полное состояние.**

**Измерено на нашем устройстве:**

| | до handshake | после handshake |
|---|---|---|
| уникальных тегов | **44** | **96…102** |

**Что раскрывается только после handshake:**

| блок | теги |
|---|---|
| компрессор | `0x46:0x01..0x08` — все 8 параметров |
| EQ-полосы | `0x91..0x94` × `0x01..0x0a` — 40 параметров |
| EQ-переключатели | `0x9b:0x0f`, `0x10`, `0x12`, `0x13` |
| прочее | `0x11:0x1e`, `0x11:0x25` |

> **Это самая дорогая ошибка проекта.** Компрессор и EQ считались
> «недоступными через HID», потому что handshake не отправлялся.
> Источник открытия: [NTMan/topping-m62](https://github.com/NTMan/topping-m62)
> (`PROTOCOL.md`, CC0).

### 3.0b Периодический ANNOUNCE — так же обязателен

Handshake открывает двери, но **одного `0x11:0x26` при подключении мало**.

Измерено (одна длинная сессия, 60 с, Prof-режим):

```
ANNOUNCE при открытии        ->  6 тегов
ANNOUNCE повторно на 16-й с  ->  174 тега
блок 0x91 (EQ входов)        ->  18.8 с
блок 0xa1 (EQ наушников)     ->  18.9 с
```

**Без повторного ANNOUNCE EQ входов и EQ наушников не приходят вообще.**
Правило в `src/transport.js`: `0x11:0x26` каждые **15 секунд** (`ANNOUNCE_MS`).

Следствие для чтения состояния: снимок должен быть не короче **26 секунд**
в Prof-режиме. `undefined` после записи означает «не увидели за отведённое
время», а не «устройство отклонило запись».

### 3.0a Bulk push bracket

```
TT = 0x11, PP = 0x20, value = 1    — открыть
   ... N кадров состояния ...
TT = 0x11, PP = 0x20, value = 0    — закрыть
```

Так вендорское приложение отправляет состояние пачкой (в захватах — 149
кадров за 0.3 с). Обязательность bracket **не подтверждена**: ядро Linux
пишет без него, и записи применяются.

### 3.1 Устройство молчит по умолчанию

Пока не выполнена подписка, устройство **не отправляет ничего**.

### 3.2 Подписка

```
TT = 0x11, PP = 0x24, value = 1
```

Одна запись запускает поток нотификаций.

### 3.3 Keepalive — ОБЯЗАТЕЛЕН

**Подписка истекает.** Вендорское приложение повторяет `0x11/0x24` **каждые
2000 мс**. В mainline-драйвере: `TOPPING_KEEPALIVE_MS = 2000`.

> Без keepalive устройство перестаёт присылать нотификации.

### 3.4 Запрос полного состояния

```
TT = 0x11, PP = 0x26, value = 1
```

Устройство сообщает всё своё состояние.

> **Уточнение из публичной документации:** `11/26` — это НЕ запрос состояния
> в чистом виде. MCC шлёт его **после** своего bulk push, а не до. В захвате
> подключения все 162 исходящих кадра — записи, ни одного чтения.
> Возможно, `11/26` просит dump DSP-блоков. Подтверждено: после него приходят
> `0x91..0x94`.

#### ТАЙМИНГ ПОЛНОГО ДАМПА (измерено)

Устройство отдаёт статический дамп **не сразу и не при каждом подключении**.
Замеры (`probe-dump-timing.js`, `probe-dump-reacquire.js`):

| время от подписки | что приходит |
|---|---|
| ~570 мс | метры, часть компрессора, `0x44`, входы, выходы, `0x9b` |
| ~2500 мс | информационный блок `0x12` |
| ~3200 мс | настройки `0x11` |
| **~4500 мс** | **EQ `0x91..0x94` — все 40 тегов разом** |
| ~7800 мс | последние `0x62`/`0x64` |

**Практические следствия:**

1. Снимок состояния должен слушать **не меньше 6–7 секунд**. Снимок в 1 с
   вернёт ~20 адресов и не увидит ни EQ, ни компрессора.
2. Между сессиями обязательна пауза **≥ 500 мс**. При мгновенном
   переподключении устройство считает сессию той же и полный дамп **не
   отдаёт** — приходит только поток метров (46 адресов вместо ~100).
3. Повторная `0x11/0x24` на живом соединении дамп **не повторяет**.

Полный дамп — **96–102 адреса**. Меньше 90 — дамп неполный.

### 3.4a Сохранение в энергонезависимую память

```
TT = 0x11, PP = 0x05, value = 1
```

Сохраняет текущее состояние в NVRAM устройства.

> **Важно:** у карты ДВЕ памяти — live-состояние и сохранённое. Отключение
> USB **не является** power-cycle (есть батарея).

### 3.5 Порядок инициализации

1. Открыть HID-интерфейс (interface 4)
2. **`0x11/0x01` = 1 — session handshake** (обязательно, см. §3.0)
3. `0x11/0x24` = 1 — подписаться
4. `0x11/0x26` = 1 — запросить состояние
5. Стартовать таймер keepalive (каждые 2000 мс слать `0x11/0x24` = 1)
6. Читать 17-байтовые отчёты в цикле

### 3.6 Волны ответа

После подписки устройство отвечает **двумя волнами**:

| время | что приходит |
|---|---|
| ~0.9 с | состояния джеков |
| ~5.2 с | снова джеки, мьюты выходов, gain каждого подключённого входа |

**Плюс:** каждое движение ручки на передней панели приходит **сразу**.

### 3.7 Селекторы НИКОГДА не отчётываются

Устройство сообщает **события**, а у селектора источника нет физической ручки.
Поэтому:

- селектор нельзя прочитать;
- если клиент его не записал — он не знает, куда указывает выход;
- вендорское приложение именно поэтому **не спрашивает**, а **шлёт свой
  workspace целиком** при подключении.

## 4. Полная таблица контролов

### 4.1 Волумы (7 штук)

| имя | `TT` | `TT_pair` | `PP` | min | max | TLV |
|---|---|---|---|---|---|---|
| Mic-1 Analog Capture Volume | `0x21` | — | `0x04` | 0 | 88 | `topping_tlv_gain` |
| Mic-2 Analog Capture Volume | `0x22` | — | `0x04` | 0 | 88 | `topping_tlv_gain` |
| Aux Capture Volume | `0x23` | — | `0x04` | 0 | 99 | `topping_tlv_out_9` |
| Bluetooth Capture Volume | `0x25` | — | `0x04` | 0 | 99 | `topping_tlv_out_0` |
| OTG Capture Volume | `0x27` | — | `0x04` | 0 | 99 | `topping_tlv_out_0` |
| Headphone Playback Volume | `0x64` | **`0x63`** | `0x03` | 0 | 99 | `topping_tlv_out_9` |
| OTG Playback Volume | `0x62` | **`0x61`** | `0x03` | 0 | 99 | `topping_tlv_out_0` |

**Про пары:** выходы идут парами, но устройство **объявляет только второй**
элемент пары. Поэтому при записи нужно писать **оба** target'а, а слушать —
только второй.

### 4.2 Селекторы (2 штуки)

| имя | `TT` | `PP` |
|---|---|---|
| Headphone Playback Source | `0x64` | `0x02` |
| OTG Playback Source | `0x62` | `0x02` |

**Селектор отвечает только на ОДНОМ target'е пары** — в отличие от волума и
мьюта, которые надо писать в оба.

### 4.3 Таблица кривых громкости (TLV)

Диапазон **0..99**, где индекс **0 = mute**, **99 = максимум**.

**`topping_tlv_gain`** (Mic-1, Mic-2; диапазон 0..88):
```
линейно, шаг 1.00 dB на единицу
```

**`topping_tlv_out_9`** (Aux, Headphone):
```
0      : MUTE
1..19  : старт -88.00 dB, шаг 2.00 dB
20..61 : старт -51.00 dB, шаг 1.00 dB
62..99 : старт  -9.50 dB, шаг 0.50 dB
```

**`topping_tlv_out_0`** (Bluetooth, OTG IN, OTG OUT):
```
0      : MUTE
1..79  : старт -88.00 dB, шаг 1.00 dB
80..99 : старт  -9.50 dB, шаг 0.50 dB
```

> Формулировка из драйвера: «index 0 is always mute, index 99 always the
> maximum, the step is 0.5 dB above -10 dB and 1 dB below it, and the family
> that has to cover 97 dB in 98 steps takes 2 dB below -52 dB as well.»

## 5. Что протокол умеет, но не описано в драйвере

Прямая цитата из патча mainline:

> The mixer matrix, the mutes, the loopback routing, the input power and the EQ
> remain reachable only through the hidraw node.

**То есть протокол их поддерживает — просто драйвер их не экспортирует.**

Обновлено 2026-11-07: часть `TT`/`PP` **уже найдена** реверсом кода MCC
(подробно — `research/EQ-MIXER.md`, журнал `research/NOTES.md` §12).

| функция | статус | адреса / канал |
|---|---|---|
| **EQ-переключатели** | **работают** (чтение + запись) | `0x9b:0x0f`, `0x9b:0x10`, `0x9b:0x12`, `0x9b:0x13` |
| **EQ входов** | **работают** (чтение + **запись**) | `0x91..0x94` × `0x01..0x0a` (нужен handshake + ANNOUNCE) |
| **EQ наушников** | **работают** (чтение + **запись**) | `0xa1..0xaa` × `0x01..0x0a`, только Prof |
| **Компрессор** | **работает** (чтение + **запись**) | `0x46:0x01..0x08` |
| **Реверб / NR** | **работают** (чтение; запись — относительно) | `0x44:0x01..0x0f` |
| **Микшер-матрица** | **запись РАБОТАЕТ** пакетом | `0x31..0x3c`, property = источник, Q25 |
| **Loopback** | **только запись** (`IN=0` во всех захватах) | `0x51..0x58`: `0x02` источник, `0x03` gain |
| **Ducking** | **только запись** (`IN=0`) | `0x43:0x01..0x07` |
| Питание входов (48V) | не найдено | — |

**Проверка направлений** (`python src/tools/check-exact-direction.py`, 5 захватов):

```
0x51:0x02  loopback LB12 источник   OUT=3   IN=0   ТОЛЬКО ПИШЕТСЯ
0x51:0x03  loopback LB12 gain       OUT=3   IN=0   ТОЛЬКО ПИШЕТСЯ
0x33:0x15  метр Mix B L             OUT=0   IN=1589 ТОЛЬКО ЧИТАЕТСЯ
0x31:0x01  кросспойнт PB12 -> Mix A OUT=4   IN=0   ТОЛЬКО ПИШЕТСЯ
```

> **Ловушка подсчёта.** Если агрегировать по семейству `TT`, выходит
> «микшер 0x31..0x3c: IN=6753, читается». Это **метры** (`PP=0x15`),
> а не кросспойнты. Проверять надо по конкретным `TT:PP`.

### 5.0a Коды источников — полная таблица (закрыто 2026-11-08)

Взято из mainline-патча `drivers/hid/hid-topping-m62.c`, таблицы
`topping_sources[]` / `topping_source_value[]`. Патч — ровно наше
устройство (`0x152a` / `0x875c`), таблица есть в двух независимых
копиях (v7-1 и lore-p2). Совпадает с `src/controls.js`.


`*` FX — сверх таблицы драйвера, проверен нами вживую
(`0x51:0x02 = 17` при `Loopback_LB12.AudioSource = FX`).

and 5 would be». Mix D и Mix E — это шины микшера (`0x37/0x38`,

### 5.0 Как правильно проверять запись — ГЛАВНАЯ ЛОВУШКА

Проверка записи — самый ломкий момент всего проекта. Три ошибки складывались
и давали ложный вывод «не пишется»:

**1. Работающий MCC откатывает записи.** MCC держит свою копию состояния и
периодически возвращает устройство к ней. Замерено: с запущенным MCC запись
`0x46:02 = -28` не применялась 60+ секунд; после закрытия MCC применилась
за 10 секунд. **MCC должен быть ЗАКРЫТ во время записи.**

**2. Обратное чтение в той же сессии показывает кэш.** После записи в
статический параметр устройство ещё отдаёт прежнее значение в текущем
соединении. Нужен **свежий дамп** — с переподключением.

**3. Снимок короче 6 секунд не видит EQ.** См. §3.4.

**Подтверждённый протокол измерения:**

```
MCC ЗАКРЫТ
  -> снимок «до»      (переподключение, пауза 800 мс, слушать 7 с)
  -> запись
  -> пауза 10 с
  -> снимок «после»   (то же)
  -> сравнение
```

Этим методом проверено **8 из 8** параметров (2026-11-08):
`0x91:01..05` (все 5 полей EQ-полосы) и `0x46:04/05/08` — все пишутся.

Отдельно: **громкость** (`0x21:04` и др.) ведёт себя иначе — она возвращается
эхом прямо в потоке событий сразу после записи, и её видно даже в той же
сессии. Поэтому по громкости нельзя судить о DSP-параметрах.

### 5.1 Шкалы (проверены)

**Микшер — Q25** (линейное усиление):
```
0            = mute
2^25 = 33554432  = 0 dB (unity)
133582600    = +12 dB
```

**EQ-полоса — 5 полей × 2 полосы на блок:**
```
0x01..0x05  — полоса 1
0x06..0x0a  — полоса 2

0x91 + 0x92 = канал 1, 4 полосы
0x93 + 0x94 = канал 2, 4 полосы
(в workspace-INI: EQ_IN1 и EQ_IN2 по 4 полосы — сходится)

поле 1 (0x01 / 0x06) = вкл/выкл полосы   0/1
поле 2 (0x02 / 0x07) = тип фильтра        1 = peaking (дефолт)
поле 3 (0x03 / 0x08) = gain, дБ           -12..+12
поле 4 (0x04 / 0x09) = частота, Гц        (632, 1000, 7000)
поле 5 (0x05 / 0x0a) = Q × 10000          (0.7 -> 7000)
```

Все 5 полей проверены записью 2026-11-08.

**Компрессор** (из `Compressor` в INI):
```
0x01 Switch      0/1
0x02 Threshold   -36..0 dB
0x03 Ratio       ×10 (4.0 -> 40); лестница до 46.9, затем 1000000 = ∞
0x04 Attack      1..500 ms
0x05 Release     1..601 ms
0x06 Gain        0..36 dB
0x07 Mix ×?      0 (ненаблюдаемо, всегда 0)
0x08 Mix         0..100 %
```

### 5.2 Как искали (чтобы не повторять ошибку)

Простой поиск константы в exe даёт мусор — 225 «семейств». Сработал линейный
дизассемблер (capstone, x86-64) с `md.skipdata = True` плюс разрешение
rip-relative `lea` в строки `.rdata`. Это дало 223 пары «имя параметра → тег».

### 5.3 Второй канал (Thesycon DSP) — ТУПИК, причина установлена

MCC импортирует `TUSBAUDIO_SetDspProperty` / `GetDspProperty`. IOCTL найдены:
`0x80882200` (чтение), `0x80882204` (запись). **Но этот путь неработоспособен
на нашей установке:**

1. **DSP-плагина физически нет.** `tusbaudiodsp*.sys` отсутствует в System32
   и DriverStore, в реестре нет `Config\EnablePlugin`.
2. **Таблицы DSP-property ID не существует в принципе.** Из публичной копии
   `tusbaudioapi.h` (Reference Manual v1.22.0):
   > «The set of properties and their meaning is **user-defined** (defined by
   > the designer of the processing plugin). Likewise, the format of the
   > property data buffer is **user-defined**.»
3. Драйвер возвращает `0xEE000030` = `TSTATUS_NOT_SUPPORTED` ещё до проверки
   состояния устройства.

**Вывод: никакой перебор ID здесь не поможет. Единственный канал — HID.**

### 5.4 Расшифровка кодов статуса драйвера

База `0xE0000000`, в user-mode приходит как `0xEE0000xx`.

| код | TSTATUS | смысл |
|---|---|---|
| `0xEE000004` | `TSTATUS_REJECTED` | отвергнуто |
| `0xEE000030` | `TSTATUS_NOT_SUPPORTED` | **функция не поддерживается** (плагин) |
| `0xEE000041` | — | нулевой аргумент |
| `0xEE000043` | — | `inSize != outSize` |
| `0xEE000045` | — | неверный размер |
| `0xEE000048` | `TSTATUS_INVALID_HANDLE` | неверный handle |
| `0xEE000049` | — | неверное состояние |
| `0xEE000053` | `TSTATUS_INVALID_MODE` | не то состояние `[dev+0x4c4]` |
| `0xEE000070` | — | нет списка устройств |

### 5.5 Рабочие IOCTL (без MCC)

| IOCTL | размер | что отдаёт |
|---|---|---|
| `0x80882004` | 24 | версии: `6, 16, 6, 16, 0, 0` |
| `0x80882100` | 132 | sample rates: `44100`, `48000` |
| `0x80882210` | 4 | `in=0 -> 16`, `in=1 -> 10` |

## 7. Безопасность

| правило | причина |
|---|---|
| **Никогда не писать в interface 3** | DFU; случайная запись → нерабочее устройство |
| Не трогать `TUSBAUDIO_*DFU*` без нужды | обновление прошивки, риск |
| **Session handshake `11/01` перед работой** | без него состояние неполное |
| Keepalive обязателен | иначе устройство замолкает |
| Проверять CRC при чтении | драйвер так делает |
| При записи `TT`/`PP` вне таблицы — сначала уточнить | неизвестное поведение |
| Учитывать отложенное применение | состояние фиксируется при следующем цикле MCC |
