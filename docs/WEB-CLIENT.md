# Веб-сервис M62: архитектура

Документ описывает, как устроен сервис, который позволяет владельцу
TOPPING M62 настраивать карту из браузера без M Control Center.

Написан как основа для ревью: здесь только то, что можно проверить
по коду, и явно отмечено, что не проверено.

---

## 1. Задача

Владелец M62 открывает страницу, подключает карту, настраивает её.
Ничего не устанавливая. M Control Center (дальше MCC) — официальная
программа — при этом не нужна.

Ограничение, из которого всё следует: **удалённый сервер не видит
USB посетителя.** Данные карты не могут уйти на сервер и вернуться,
потому что сервер физически не подключён к устройству.

Отсюда единственная рабочая схема: код протокола исполняется **в
браузере посетителя**, а устройство открывается через WebHID.

---

## 2. Два способа добраться до карты

### A. WebHID прямо в странице (основной)

Браузер открывает vendor-интерфейс карты, страница говорит с ней
напрямую. Сервер отдаёт только статические файлы и **не трогает
устройство** (автозахват выключен по умолчанию).

```
браузер ──── WebHID ────► M62 (interface 4)
   ▲
   │ HTTP (html + js)
сервер (только файлы)
```

**Плюсы:** данные не покидают компьютер, сервер можно выключить после
загрузки страницы.
**Минусы:** нужен Chrome/Edge 89+ (Firefox и Safari WebHID не умеют),
нужен HTTPS или localhost, разрешение выдаётся на каждое устройство.

### B. Локальный агент (вспомогательный)

Тот же код, но транспорт — не WebHID, а `node-hid` на машине
пользователя.

```
браузер ──── HTTP ────► агент (localhost) ──── node-hid ────► M62
```

**Плюсы:** работает и там, где WebHID нет; доступны функции, которых
в браузере нет (реестр, службы Windows).
**Минусы:** требует установки и запуска.

Оба пути используют **один и тот же код протокола**, различается
только адаптер.

## 3. Слои

```
┌──────────────────────────────────────────────┐
│ UI            web/index.html                 │  один файл, без сборки
├──────────────────────────────────────────────┤
│ Транспорт     src/transport-core.js          │  политика
│               ├── src/adapter-webhid.js      │  браузер
│               └── src/adapter-nodehid.js     │  Node
├──────────────────────────────────────────────┤
│ Протокол      src/protocol.js, crc16.js      │  кадры
├──────────────────────────────────────────────┤
│ Домен         eq-hid, comp-hid, reverb-hid,  │  адреса, шкалы
│               duck-loopback-hid, phantom-hid,│
│               mixer-tags, tags               │
├──────────────────────────────────────────────┤
│ Сервер        src/server.js (61 маршрут)     │  необязателен для A
└──────────────────────────────────────────────┘
```

### Границы, которые важны

**`transport-core.js` не знает, откуда байты.** Он получает адаптер
с методами `write`, `onData`, `close` и — для подтверждения записи
EQ — `reopen`. Всё остальное — handshake, подписка, keepalive, кеш,
коммит — внутри.

`reopen` обязателен не для красоты: блоки EQ приходят только на
первый announce **новой** сессии, поэтому подтвердить запись можно
лишь закрыв и открыв соединение. Оба адаптера его реализуют:
`adapter-nodehid` создаёт новый `HID.HID`, `adapter-webhid` делает
`device.close()` затем `device.open()` (разрешение пользователя при
этом сохраняется — повторный выбор не нужен).

Это проверяемо: в графе импортов от `adapter-webhid.js` **ноль**
`node:*`-модулей и ноль npm-пакетов (`src/tools/test-browser-modules.js`).

**Доменные модули чистые.** `eq-hid.js`, `comp-hid.js` и остальные
не тянут ничего из Node. Они собирают кадры и разбирают значения,
зная только адреса и шкалы.

**Сервер для пути A не нужен.** Он раздаёт статические файлы и
работает агентом для пути B. Важно: **сервер не захватывает
устройство при старте.** Автозахват включается только флагом
`M62_AUTOCONNECT=1` (режим агента). Иначе браузер с WebHID и сервер
с node-hid оказались бы двумя писателями на одной карте — со своими
keepalive, announce и кешами, перезаписывая настройки друг друга.

## 4. Обозначения

Прежде чем правила: **`TT:PP`** — это пара чисел, которой адресуется
параметр карты. `TT` (target) — блок: вход, выход, эффект, само
устройство. `PP` (property) — параметр внутри блока.

Примеры: `0x11:0x01` — устройство (0x11), свойство 1 (handshake).
`0x44:0x0b` — блок эффектов (0x44), свойство 11 (тип реверба).

**Кадр** — 15 байт, которые уходят в карту: `22 33 | 20 01 01 | TT | PP |
s32 | CRC16 | 66 77`. Число — 4 байта big-endian.

**Тег** — одно значение, которое карта присылает. «44 тега» значит
44 адреса со значениями. Одно и то же число адресов в разных местах
этого документа означает одно и то же: количество уникальных пар
`TT:PP`, полученных от карты в одном сеансе.

**Дамп** — ответ карты на `0x11:0x26`: она присылает набор тегов
целиком. **Брекет** (bulk-push) — пара кадров `0x11:0x20 = 1` и
`0x11:0x20 = 0`; всё, что отправлено между ними, карта применяет как
одно целое.

## 5. Протокол: правила, которые нельзя нарушить

Правила найдены экспериментально. Нарушение любого из них даёт
**молчаливый отказ** — карта не отвечает ошибкой, просто ничего не
происходит.

| Правило | Почему | Проверено |
|---|---|---|
| handshake `0x11:0x01 = 1` первым | без него карта не отдаёт компрессор и EQ: 44 тега вместо 96 | да |
| keepalive `0x11:0x24` каждые 2 с | без него карта замолкает | да |
| **EQ приходит только на ПЕРВЫЙ announce новой сессии** | повторный announce в той же сессии даёт 48 адресов вместо 91 и **0 EQ-адресов** вместо 40 | да, замерено |
| запись EQ: держать сессию ≥ 2 с | прошивка коммитит не мгновенно; < 2 с — теряется | да, замерено |
| **подтвердить запись EQ можно только НОВОЙ сессией** | в той же сессии EQ повторно не приходит, `readViaDump` вернёт кеш | да |
| **запись микшера — только внутри брекета** | одиночные кадры в `0x31..0x3c` карта игнорирует | да |
| выходы писать в ОБА адреса пары | иначе каналы разъезжаются | да |
| реверб: сначала тип, потом параметры | при Bypass параметры игнорируются | да |
| interface 3 (DFU) не трогать | можно превратить карту в кирпич | — |

**Правило про interface 3 действует не в ядре, а в адаптере.** Ядро
получает уже открытое устройство и не выбирает его. Фильтр по
vendor-интерфейсу и проверку `collections[].interface === 4` делает
`adapter-webhid.js` (`pickVendorInterface`). Гарантия ядра начинается
после того, как устройство выбрано.

### Тонкость, на которой легко ошибиться

Периодический announce (`0x11:0x26` каждые 15 с) нужен **не для EQ** —
он возвращает общий дамп тегов. Блоки EQ приходят однократно, на
первом announce сессии.

Из этого следует неочевидное: **`readViaDump()` в уже открытой сессии
не может подтвердить запись EQ.** Повторный announce не вернёт
блоки, и функция отдаст то, что лежит в кеше, — то есть наши
собственные записанные значения. Это выглядит как «применено»,
даже если карта запись отвергла.

Поэтому в коде:

- `readViaDump()` возвращает `__fromCache: true` и
  `__dumpComplete: false`, когда EQ повторно не пришли;
- `readFresh()` закрывает сессию, открывает новую и ждёт первый
  announce — только это даёт правду;
- `POST /api/eq/band` отвечает `applied: "unverified"`, а не
  `"confirmed"`, если дамп не пришёл.

Замер, на котором это основано (`prove-announce-eq-rule.js`):

```
announce #1 в новой сессии:  91 адрес, 40 EQ
announce #2 в той же сессии: 48 адресов,  0 EQ
announce #3 в той же сессии: 48 адресов,  0 EQ
новая сессия, #1:            91 адрес, 40 EQ
```

Все эти правила собраны в `transport-core.js` и доменных модулях,
чтобы вызывающий код не мог сделать неправильно.

## 6. Что умеет UI

Проверено сборкой кадров (`src/tools/test-ui-frames.js`, 39/39):

| Группа | Управление | Адреса |
|---|---|---|
| Выходы | громкость HP, MUTE HP/OTG | `0x63/0x64:03`, `0x61..0x64:04` |
| Входы | усиление ×5 | `0x21/0x22/0x23/0x25/0x27:04` |
| Питание | 48V IN1/IN2 | `0x21/0x22:03` |
| Реверб | тип, dry/wet, room, decay, width | `0x44:0b, 08, 09, 0a, 0f` |
| Компрессор | switch, threshold, ratio, attack, release, mix | `0x46:01..08` |
| EQ входа IN1 | 4 полосы × (включение + gain) | `0x91` (полосы 1,2), `0x92` (полосы 3,4) |

**Про EQ важно не запутаться.** Четыре адреса `0x91..0x94` — это
четыре **блока**, а не четыре полосы:

```
IN 1:  0x91 = полосы 1 и 2      0x92 = полосы 3 и 4
IN 2:  0x93 = полосы 1 и 2      0x94 = полосы 3 и 4
```

В каждом блоке по 5 свойств: включение (`0x01`/`0x06`), тип
(`0x02`/`0x07`), gain (`0x03`/`0x08`), частота (`0x04`/`0x09`),
Q (`0x05`/`0x0a`). Итого 40 адресов на вход.

Сейчас страница управляет **только IN 1** и только двумя свойствами
из пяти — включением и gain. Тип, частота и Q не выведены.

**Не сделано:**

| Что | Почему не сделано |
|---|---|
| EQ входа IN 2 (`0x93`, `0x94`) | протокол тот же, нужен UI |
| EQ наушников (`0xa1..0xaa`, 10 полос × 2 канала) | только в Prof-режиме; протокол известен, UI нет |
| тип, частота, Q фильтров EQ | адреса известны, нужны контролы |
| микшер (5 шин × 11 источников) | запись требует брекета, **применение не подтверждено чтением** |
| loopback (4 пары) | карта не отдаёт назад |
| ducking (маска + параметры) | карта не отдаёт назад |
| сохранение сцен | нет хранилища — план в §11, фаза 4 |

## 7. Защита от опасных операций

Три вещи могут навредить оборудованию или слуху:

1. **48 В на входе.** Включается только после `confirm()` с
   объяснением, что это фантомное питание для конденсаторного
   микрофона. На линейном входе может повредить оборудование.

2. **Громкий звук.** Если джек воткнут и MUTE не стоит, UI
   показывает предупреждение и кнопку «Заглушить».

3. **Прошивка.** Не реализовано намеренно: запись через DFU не
   воспроизведена, проверка целостности на карте не установлена.

## 9. Ограничения, о которых надо сказать пользователю

1. **Только Chrome и Edge 89+.** Firefox и Safari WebHID не
   поддерживают. Это не наше ограничение, а состояние браузеров.

2. **HTTPS обязателен.** На `http://` (кроме localhost) `navigator.hid`
   отсутствует. Для публичного домена нужен сертификат.

3. **MCC должен быть закрыт.** Он занимает устройство; при
   одновременной работе две программы перезаписывают настройки друг
   друга.

4. **Часть параметров не читается никогда.** Микшер, loopback,
   ducking и селекторы источников карта не присылает назад ни в
   каком виде. Их состояние надо хранить у себя.

5. **Громкость выхода не читается до первого движения ручки.**
   Пока её не тронули, карта молчит. Показывать «0» нельзя — это
   будет ложь в опасную сторону: ноль означает mute, а выход может
   быть на максимуме.

6. **Sample rate и buffer size в браузере изменить нельзя.**
   Sample rate хранится в реестре Windows: читать его можно
   (`/api/audio-params` читает без MCC), записать — нет, потому что
   ACL ключа не даёт прав даже администратору. Buffer size живёт в
   драйвере. Это настройки ОС, а не протокола карты.

7. **Состояние не сохраняется на карте автоматически.** Часть
   параметров карта помнит сама, часть — нет.

## 10. Как проверить самому

Порядок важен: третий скрипт требует запущенного сервера.

```bash
# 1. ядро на живом устройстве (карта подключена, MCC закрыт)
node src/tools/test-transport-core.js
# ожидаемо: 5 из 5

# 2. кадры управления — устройство не нужно
node src/tools/test-ui-frames.js
# ожидаемо: 39 из 39

# 3. сервер (в отдельном окне, оставить работать)
$env:M62_PORT='8898'; node src/server.js

# 4. клиентские модули без Node — НУЖЕН сервер из шага 3
node src/tools/test-browser-modules.js --port 8898
# ожидаемо: 22 из 22

# 5. страница в браузере
#    открыть http://127.0.0.1:8898/ — в Chrome или Edge
#    или запустить: .\open-web-client.ps1
```

Проверить руками в браузере (headless не подходит: WebHID требует
видимого окна и выбора устройства):

1. нажать «Подключить», выбрать M62 в диалоге;
2. статус должен стать «подключено»;
3. через ~6 с заполнятся карточки, «адресов получено» > 80;
4. воткнуть наушники — «наушники подключены» станет «да».

### Фаза 4. Сцены

**Решение принято: `localStorage` браузера.** Обоснование: сервер не
должен знать, что пользователь настроил, — данные карты не покидают
его компьютер. Серверное хранилище потребовало бы идентификации и
хранения чужого состояния без нужды.

| Файл | Что изменить |
|---|---|
| `web/scenes.js` | **новый**: `save(name)`, `list()`, `load(name)`, `remove(name)` |
| `web/index.html` | кнопки сохранить/загрузить/удалить |

Формат записи:

```json
{
  "version": 1,
  "name": "вокал",
  "createdAt": "2026-11-14T00:00:00.000Z",
  "params": { "0x44:0x0b": 3, "0x46:0x02": -20, "0x91:0x03": 4 },
  "unreadable": ["mixer", "loopback", "ducking", "selectors"]
}
```

`params` — только те адреса, которые карта отдаёт назад. `unreadable`
перечисляет группы, которые карта не читает: сцена их не сохраняет и
при загрузке не трогает. Так сцена не врёт о том, что восстановит.

Проверка: сохранить, изменить параметр, загрузить — значение вернулось.
