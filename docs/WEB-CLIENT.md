# Веб-сервис M62: архитектура

Документ описывает, как устроен сервис, который позволяет владельцу
TOPPING M62 настраивать карту из браузера без M Control Center.

Написан как основа для ревью: здесь только то, что можно проверить
по коду, и явно отмечено, что не проверено.

---

## 1. Задача

Владелец M62 открывает страницу, подключает карту, настраивает её.
Ничего не устанавливая. M Control Center (дальше MCC) — официальная
программа — при этом не нужна.

Ограничение, из которого всё следует: **удалённый сервер не видит
USB посетителя.** Данные карты не могут уйти на сервер и вернуться,
потому что сервер физически не подключён к устройству.

Отсюда единственная рабочая схема: код протокола исполняется **в
браузере посетителя**, а устройство открывается через WebHID.

---

## 2. Два способа добраться до карты

### A. WebHID прямо в странице (основной)

Браузер открывает vendor-интерфейс карты, страница говорит с ней
напрямую. Сервер отдаёт только статические файлы и **не трогает
устройство** (автозахват выключен по умолчанию).

```
браузер ──── WebHID ────► M62 (interface 4)
   ▲
   │ HTTP (html + js)
сервер (только файлы)
```

**Плюсы:** данные не покидают компьютер, сервер можно выключить после
загрузки страницы.
**Минусы:** нужен Chrome/Edge 89+ (Firefox и Safari WebHID не умеют),
нужен HTTPS или localhost, разрешение выдаётся на каждое устройство.

### B. Локальный агент — НЕ РЕАЛИЗОВАН

Замысел: браузер говорит с локальным сервером по HTTP, сервер
держит устройство через `node-hid`.

```
браузер ──── HTTP ────► агент (localhost) ──── node-hid ────► M62
```

**Задумывалось:** работает там, где WebHID нет; доступны функции,
которых в браузере нет (реестр, службы Windows).
**Минусы:** требует установки и запуска.

**Состояние на сегодня: агент есть, клиента к нему нет.**

- Сервер `src/server.js` работает и отдаёт 61 маршрут, но страница
  `web/index.html` не делает ни одного HTTP-запроса (ноль вхождений
  `fetch`, `/api`, WebSocket). То есть сервер сегодня вызывают только
  собственные тесты.
- **Политика протокола написана дважды.** Страница использует
  `src/transport-core.js`, сервер — `src/transport.js` (`M62Transport`).
  Оба реализуют handshake, keepalive, announce, коммит EQ и чтение
  новой сессией. Копии уже разошлись: `ANNOUNCE_MS = 15000` объявлен
  независимо в обоих файлах.

Следствие: утверждение «оба пути используют один и тот же код, и
различается только адаптер» верно только для пути A. Для цели §1
(«ничего не устанавливая») путь B не нужен; если он понадобится,
сначала надо перевести сервер на ядро + `adapter-nodehid`, иначе
правку политики придётся делать в двух местах.

## 3. Слои

```
┌──────────────────────────────────────────────┐
│ UI            web/index.html                 │  один файл, без сборки
├──────────────────────────────────────────────┤
│ Транспорт     src/transport-core.js          │  политика (путь A)
│               ├── src/adapter-webhid.js      │  браузер
│               └── src/adapter-nodehid.js     │  Node
├──────────────────────────────────────────────┤
│ Протокол      src/protocol.js, crc16.js      │  кадры
├──────────────────────────────────────────────┤
│ Домен         eq-hid, comp-hid, reverb-hid,  │  адреса, шкалы
│               duck-loopback-hid, phantom-hid,│
│               mixer-tags, tags               │
├──────────────────────────────────────────────┤
│ Сервер        src/server.js (61 маршрут)     │  путь B, ОТДЕЛЬНАЯ
│               src/transport.js               │  реализация политики
└──────────────────────────────────────────────┘
```

**Сервер стоит на своей реализации транспорта, а не на ядре.** Это
не описание замысла, а факт: `src/server.js` импортирует
`M62Transport` из `src/transport.js`, где handshake, keepalive,
announce, `writeEqWithCommit` и `readFresh` написаны заново. Ядро
`transport-core.js` сервер не использует.

Практическое следствие: любая правка политики протокола делается в
двух файлах. Так уже случилось с `ANNOUNCE_MS` и с ложным
подтверждением EQ (§9 ниже).

### Границы, которые важны

**`transport-core.js` не знает, откуда байты.** Он получает адаптер
с методами `write`, `onData`, `close` и — для подтверждения записи
EQ — `reopen`. Всё остальное — handshake, подписка, keepalive, кеш,
коммит — внутри.

`reopen` обязателен не для красоты: блоки EQ приходят только на
первый announce **новой** сессии, поэтому подтвердить запись можно
лишь закрыв и открыв соединение. Оба адаптера его реализуют:
`adapter-nodehid` создаёт новый `HID.HID`, `adapter-webhid` делает
`device.close()` затем `device.open()` (разрешение пользователя при
этом сохраняется — повторный выбор не нужен).

Это проверяемо: в графе импортов от `adapter-webhid.js` **ноль**
`node:*`-модулей и ноль npm-пакетов (`src/tools/test-browser-modules.js`).

**Доменные модули чистые.** `eq-hid.js`, `comp-hid.js` и остальные
не тянут ничего из Node. Они собирают кадры и разбирают значения,
зная только адреса и шкалы.

**Сервер для пути A не нужен.** Он раздаёт статические файлы (этим
путём A и пользуется) и задуман как агент для пути B, которого
пока нет. Важно: **сервер не захватывает устройство при старте.**
Автозахват включается только флагом `M62_AUTOCONNECT=1`. Иначе
браузер с WebHID и сервер с node-hid оказались бы двумя писателями
на одной карте — со своими keepalive, announce и кешами.

## 4. Обозначения

Прежде чем правила: **`TT:PP`** — это пара чисел, которой адресуется
параметр карты. `TT` (target) — блок: вход, выход, эффект, само
устройство. `PP` (property) — параметр внутри блока.

Примеры: `0x11:0x01` — устройство (0x11), свойство 1 (handshake).
`0x44:0x0b` — блок эффектов (0x44), свойство 11 (тип реверба).

**Кадр** — 15 байт, которые уходят в карту: `22 33 | 20 01 01 | TT | PP |
s32 | CRC16 | 66 77`. Число — 4 байта big-endian.

**Тег** — одно значение, которое карта присылает. «44 тега» значит
44 адреса со значениями. Одно и то же число адресов в разных местах
этого документа означает одно и то же: количество уникальных пар
`TT:PP`, полученных от карты в одном сеансе.

**Дамп** — ответ карты на `0x11:0x26`: она присылает набор тегов
целиком. **Брекет** (bulk-push) — пара кадров `0x11:0x20 = 1` и
`0x11:0x20 = 0`; всё, что отправлено между ними, карта применяет как
одно целое.

## 5. Протокол: правила, которые нельзя нарушить

Правила найдены экспериментально. Нарушение любого из них даёт
**молчаливый отказ** — карта не отвечает ошибкой, просто ничего не
происходит.

| Правило | Почему | Проверено |
|---|---|---|
| handshake `0x11:0x01 = 1` первым | без него карта не отдаёт компрессор и EQ: 44 тега вместо 96 | да |
| keepalive `0x11:0x24` каждые 2 с | без него карта замолкает | да |
| **EQ приходит только на ПЕРВЫЙ announce новой сессии** | повторный announce в той же сессии даёт 48 адресов вместо 91 и **0 EQ-адресов** вместо 40 | да, замерено |
| запись EQ: держать сессию ≥ 2 с | прошивка коммитит не мгновенно; < 2 с — теряется | да, замерено |
| **после hold нужна ещё пауза ~4 с до закрытия сессии** | иначе запись тоже теряется, хотя кадры формально верные | да, замерено 5/5 |
| **подтвердить запись EQ можно только НОВОЙ сессией** | в той же сессии EQ повторно не приходит, `readViaDump` вернёт кеш | да |
| **запись микшера — только внутри брекета** | одиночные кадры в `0x31..0x3c` карта игнорирует | да |
| выходы писать в ОБА адреса пары | иначе каналы разъезжаются | да |
| реверб: сначала тип, потом параметры | при Bypass параметры игнорируются | да |
| interface 3 (DFU) не трогать | можно превратить карту в кирпич | — |

**О числах адресов.** В документе встречаются разные значения —
96, 91, 92, 102 — и это разные замеры в разных условиях, а не
ошибка:

| Число | Что это |
|---|---|
| 96 | полный набор после handshake (замер `src/protocol.js`) |
| 91 | первый announce новой сессии, полный дамп |
| 92 | `readViaDump()` в уже открытой сессии — по правилу выше это **кеш**, не свежее чтение |
| 102 | сессия при идущем звуке (добавляются семейства `0x31..0x36`, `0x39`) |

**Правило про interface 3 действует не в ядре, а в адаптере.** Ядро
получает уже открытое устройство и не выбирает его. Фильтр по
vendor-интерфейсу и проверку `collections[].interface === 4` делает
`adapter-webhid.js` (`pickVendorInterface`). Гарантия ядра начинается
после того, как устройство выбрано.

### Тонкость, на которой легко ошибиться

Периодический announce (`0x11:0x26` каждые 15 с) нужен **не для EQ** —
он возвращает общий дамп тегов. Блоки EQ приходят однократно, на
первом announce сессии.

Из этого следует неочевидное: **`readViaDump()` в уже открытой сессии
не может подтвердить запись EQ.** Повторный announce не вернёт
блоки, и функция отдаст то, что лежит в кеше, — то есть наши
собственные записанные значения. Это выглядит как «применено»,
даже если карта запись отвергла.

Поэтому в коде:

- `readViaDump()` возвращает `__fromCache: true` и
  `__dumpComplete: false`, когда EQ повторно не пришли;
- `readFresh()` закрывает сессию, открывает новую и ждёт первый
  announce — только это даёт правду;
- `POST /api/eq/band` отвечает `applied: "unverified"`, а не
  `"confirmed"`, если дамп не пришёл.

Замер, на котором это основано (`prove-announce-eq-rule.js`):

```
announce #1 в новой сессии:  91 адрес, 40 EQ
announce #2 в той же сессии: 48 адресов,  0 EQ
announce #3 в той же сессии: 48 адресов,  0 EQ
новая сессия, #1:            91 адрес, 40 EQ
```

Все эти правила собраны в `transport-core.js` и доменных модулях,
чтобы вызывающий код не мог сделать неправильно.

## 6. Что умеет UI

Проверено сборкой кадров (`src/tools/test-ui-frames.js`, 39/39):

| Группа | Управление | Адреса |
|---|---|---|
| Выходы | громкость HP, MUTE HP/OTG | `0x63/0x64:03`, `0x61..0x64:04` |
| Входы | усиление ×5 | `0x21/0x22/0x23/0x25/0x27:04` |
| Питание | 48V IN1/IN2 | `0x21/0x22:03` |
| Реверб | тип, dry/wet, room, decay, width | `0x44:0b, 08, 09, 0a, 0f` |
| Компрессор | switch, threshold, ratio, attack, release, mix | `0x46:01..08` |
| EQ входа IN1 | 4 полосы × (включение + gain) | `0x91` (полосы 1,2), `0x92` (полосы 3,4) |

**Про EQ важно не запутаться.** Четыре адреса `0x91..0x94` — это
четыре **блока**, а не четыре полосы:

```
IN 1:  0x91 = полосы 1 и 2      0x92 = полосы 3 и 4
IN 2:  0x93 = полосы 1 и 2      0x94 = полосы 3 и 4
```

В каждом блоке по 5 свойств: включение (`0x01`/`0x06`), тип
(`0x02`/`0x07`), gain (`0x03`/`0x08`), частота (`0x04`/`0x09`),
Q (`0x05`/`0x0a`). Итого 40 адресов на вход.

### Чего страница не умеет и почему

| Что | Почему |
|---|---|
| Прочитать микшер с карты | **карта не отдаёт его** — проверено: 1600 записей, 0 чтений |
| Прочитать loopback (`0x51..0x58`) | приходит только в bulk push, обратно нет |
| Прочитать ducking (`0x43`) | то же |
| Подтвердить запись микшера | метры живые, но только при идущем звуке |
| Обновить прошивку | запись через DFU не воспроизведена; риск кирпича |
| Sample rate / buffer size | в браузере недоступны; через агент читаются, запись запрещена системой |

Микшер и сцены — единственные места, где UI показывает не
прочитанное с карты, а **нашу модель**. Это помечено в самом
интерфейсе, а не только здесь.

## 7. Защита от опасных операций

Три вещи могут навредить оборудованию или слуху:

1. **48 В на входе.** Включается только после `confirm()` с
   объяснением, что это фантомное питание для конденсаторного
   микрофона. На линейном входе может повредить оборудование.

2. **Громкий звук.** Если джек воткнут и MUTE не стоит, UI
   показывает предупреждение и кнопку «Заглушить».

3. **Прошивка.** Не реализовано намеренно: запись через DFU не
   воспроизведена, проверка целостности на карте не установлена.

Если у пользователя другая версия, поведение может отличаться.

## 9. Ограничения, о которых надо сказать пользователю

1. **Только Chrome и Edge 89+.** Firefox и Safari WebHID не
   поддерживают. Это не наше ограничение, а состояние браузеров.

2. **HTTPS обязателен.** На `http://` (кроме localhost) `navigator.hid`
   отсутствует. Для публичного домена нужен сертификат.

3. **MCC должен быть закрыт — но не потому, что «занимает
   устройство».** Interface 4 открывается вторым читателем: MCC
   держит карту, а мы при этом читаем состояние без ошибок
   (`research/NOTES.md` §14). Настоящий риск другой и опаснее:
   MCC считает себя хозяином настроек и **откатывает** чужие
   записи, как только перечитывает состояние. Замер: запись
   `0x46:0x02` при запущенном MCC не применялась 60+ секунд,
   без MCC — за 10.

   Практический сценарий: UI показал «записано», а карта вернулась
   к прежнему значению, и пользователь этого не заметил. Поэтому
   MCC нужно закрывать, а не «потому что не откроется».

4. **Часть параметров не читается никогда.** Микшер, loopback,
   ducking и селекторы источников карта не присылает назад ни в
   каком виде. Их состояние надо хранить у себя.

5. **Громкость выхода не читается до первого движения ручки.**
   Пока её не тронули, карта молчит. Показывать «0» нельзя — это
   будет ложь в опасную сторону: ноль означает mute, а выход может
   быть на максимуме.

6. **Sample rate и buffer size в браузере недоступны.** В пути A
   (WebHID, без установки) их нет вовсе: sample rate хранится в
   реестре Windows, а страница не делает HTTP-запросов. Через
   локальный агент sample rate **читается** (`/api/audio-params`
   работает без MCC), запись запрещена: ACL ключа не даёт прав даже
   администратору. Buffer size живёт в драйвере. Это настройки ОС,
   а не протокола карты.

7. **Состояние не сохраняется на карте автоматически.** Часть
   параметров карта помнит сама, часть — нет.

## 10. Как проверить самому

Порядок важен: третий скрипт требует запущенного сервера.

```bash
# 1. ядро на живом устройстве (карта подключена, MCC закрыт)
node src/tools/test-transport-core.js
# ожидаемо: 5 из 5

# 2. кадры управления — устройство не нужно
node src/tools/test-ui-frames.js
# ожидаемо: 66 из 66

# 3. сервер (в отдельном окне, оставить работать)
$env:M62_PORT='8898'; node src/server.js

# 4. клиентские модули без Node — НУЖЕН сервер из шага 3
node src/tools/test-browser-modules.js --port 8898
# ожидаемо: 22 из 22

# 5. надёжность бекенда — НУЖЕН тот же сервер, и ТОТ ЖЕ порт
$env:M62_PORT='8898'; node src/tools/test-robustness.js
# ожидаемо: 20 из 20
# ⚠ скрипт читает M62_PORT, но НЕ принимает --port. Без переменной
#   он пойдёт на 8892 и выдаст «0/20» — это не поломка, а промах портом.
# ⚠ не запускать два прогона одновременно: они делят состояние карты.

# 6. страница в браузере
#    открыть http://127.0.0.1:8898/ — в Chrome или Edge
#    или запустить: .\open-web-client.ps1

# 7. сцены и модель микшера — устройство и сервер НЕ нужны
node src/tools/test-scenes.js
# ожидаемо: 35 из 35
```

Проверить руками в браузере (headless не подходит: WebHID требует
видимого окна и выбора устройства):

1. нажать «Подключить», выбрать M62 в диалоге;
2. статус должен стать «подключено»;
3. через ~6 с заполнятся карточки, «адресов получено» > 80;
4. воткнуть наушники — «наушники подключены» станет «да».

| Файл | Что изменить | Состояние |
|---|---|---|
| `src/tools/audit-mixer-in-captures.py` | **новый**: проверить на всех захватах, читается ли микшер | **0 чтений** (см. §8) |

**Блокирующий вопрос решён — но отрицательно.** Микшер прочитать
нельзя. Это не недоработка и не ошибка метода: прогнаны все 11
захватов (494 МБ). Кросспоинты `0x31..0x3c:0x01..0x14` записаны
**1600 раз** (200 в каждом захвате) и **ни разу** не пришли в IN.
Метод проверен на других семействах в тех же файлах — работает.

Сам MCC устроен так же: он держит микшер в workspace-INI
(`Mixer_IN12`, `MixB_GAIN`), а не читает с карты.

**Как это отражено в UI.** Таблица показывает нашу модель из
`localStorage`, а над ней стоит предупреждение, что состояние не
с карты. Это не формальность: если пользователь трогал микшер в
MCC или карта сбросилась, мы об этом не узнаем и обязаны сказать.

**Подтверждение записи.** Физически возможно — метрами шин
(`0x31..0x34:0x15`). В захвате они дают 129 уникальных значений,
то есть живые и детальные. Но есть жёсткое ограничение: **метры
приходят только когда на карту идёт звук**. Замер в тишине: 89
адресов, семейств `0x31..0x36` и `0x39` нет вовсе. Со звуком: 102
адреса, 11 живых. Поэтому UI пишет `unverified` и не выдаёт
«подтверждено» без реального сигнала.

### Фаза 4. Сцены — СДЕЛАНО

**Решение принято: `localStorage` браузера.** Обоснование: сервер не
должен знать, что пользователь настроил, — данные карты не покидают
его компьютер. Серверное хранилище потребовало бы идентификации и
хранения чужого состояния без нужды.

| Файл | Что изменить | Состояние |
|---|---|---|
| `web/scenes.js` | **новый**: `saveScene`, `listScenes`, `getScene`, `removeScene` | написано |
| `src/tools/test-scenes.js` | **новый**: сцены и модель микшера без устройства | 35/35 |
| `web/index.html` | кнопки сохранить/загрузить/удалить | сделано |

**Сцена разделена на две части — и это главное решение.**

```json
{
  "version": 1,
  "name": "вокал",
  "createdAt": "2026-11-16T00:00:00.000Z",
  "params": { "0x44:0x0b": 3, "0x46:0x02": -20, "0x91:0x03": 4 },
  "model":  { "b": { "pb12": { "l": 0, "r": 0 } } },
  "unreadable": ["mixer", "loopback", "ducking", "selectors"]
}
```

`params` — адреса, которые карта отдаёт назад. Их записываем и можем
перечитать. `model` — матрица микшера, которую карта не отдаёт;
записываем, но не утверждаем, что так было на карте.

`unreadable` — не комментарий, а данные: интерфейс показывает этот
список пользователю после загрузки сцены. Тест проверен
контрпримером — если список очистить, две проверки падают.

Метры (живые показания вроде `0x31:0x15`) в сцену не попадают: это
не настройка, а сигнал, он меняется каждую секунду.

## 12. Что осталось открытым

1. **Микшер: применяется ли запись — и можно ли это подтвердить в
   тишине?** Ответ по чтению получен и он отрицательный: карта не
   отдаёт микшер (см. §8). Подтверждение
   физически возможно метрами шин, но **только при идущем звуке**:
   в тишине семейств `0x31..0x36` и `0x39` в дампе нет вовсе.

   Открыто: применить запись и убедиться, что метр изменился (нужен
   звук на карте). Это единственный оставшийся способ поставить
   «подтверждено» вместо «unverified».

2. **`Mic Capture Switch` — единственная дыра в покрытии.** Восемь
   loopback-каналов захвата приходят заглушенными, пока этот
   переключатель не включён. Но это **UAC-контрол** (USB Audio
   Class), а не HID-тег: через interface 4 до него не достать.
   Нужен доступ к ОС (ALSA/PipeWire/Windows audio APIs) — то есть
   только через локальный агент, не из браузера.

3. **Есть ли у M62 экспандер.** В MCC нашлась кнопка `EXP` в общем
   меню эффектов, но она обслуживается общим кодом с KB22. Доказать
   наличие или отсутствие у M62 пока нельзя. Проверяется захватом
   трафика MCC при переключении панели EXP.

4. **Реверс прошивки: следующий шаг.** Архитектура найдена
   (**xCore XS3**, чип **XMOS XU316**), образ разбирается в Ghidra с
   модулем из issue #5835. См. `research/FIRMWARE-REVERSE.md`.

   Открыто: найти точки входа, разметить функции, разобрать таблицы
   параметров DSP. Это путь к пониманию, можно ли добавить эффекты
   (например, delay или экспандер) в саму карту.

5. **Дамп флеш-памяти.** Самый перспективный шаг для прошивки:
   прочитать QSPI-флеш программатором (CH341A + прищепка). Дамп
   может быть чище, чем файл обновления, который передаёт MCC.

   Подробнее: `research/PROGRAMMERS.md`, `research/BOARD-PHOTOS.md`.

6. **Проверка целостности прошивки.** На стороне Windows её нет
   (проверено: драйвер не содержит работы с DFU, MCC не хранит хеш).
   Есть ли она на карте — неизвестно, и безопасно проверить нельзя:
   единственный способ — записать заведомо битый образ, а это риск
   кирпича.
