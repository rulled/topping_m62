## Comprehension paraphrase

Наивный читатель понял документ так: проект хочет одну страницу в
интернете, где владелец M62 подключает карту и пользуется ею без
установки чего-либо, кроме браузера. Поскольку удалённый сервер
физически не видит USB посетителя, документ сравнивает три способа
добраться до устройства: **A** — WebHID в странице, **B** — маленький
локальный агент на `http://127.0.0.1:<порт>`, **C** — WebHID, при
неудаче агент. A оценён в 85% маршрутов бекенда, B в 100%.

**Чего читатель не смог восстановить:** что такое «маршрут» — слово
нигде не определено и ни на что не ссылается, поэтому непонятно, как
«53 из 62 маршрутов» превращается в «85% функций» и в «да для 85%»
пользователей.

## Приоритизированные находки

### 1. Цифра 85% не соответствует тому, что выдаёт указанный инструмент — Severity: Blocker
* **Линза:** `design_critic` B1 (также: `zoom_out` M1, `comprehension` 1, `implementation_readiness` 5)
* **Область:** §2A L33–L41, §3 таблица, §8
* **Расхождение:** все четыре ревьюера независимо проверили
  `node src/tools/webhid-coverage.js` и обнаружили одно и то же.
  Инструмент вырезает блоки `try/catch` перед сопоставлением маркеров,
  поэтому пять маршрутов, которые документ сам объявляет недоступными,
  попали в «доступно»:

  ```
  GET/POST /api/audio-params    sample rate — только UIAutomation
  POST /api/eq/open             открывает окно MCC
  POST /api/compressor/open     открывает окно MCC
  POST /api/compressor/close    закрывает окно MCC
  ```

  Плюс инструмент теряет `GET /api/mode` и `POST /api/mode` из
  недоступных, хотя `POST /api/mode` останавливает и запускает MCC.
  То есть 85% завышено ровно на ту функциональность, которую документ
  сам называет недоступной.
* **Рекомендация:** пересчитать по возможностям, а не по маршрутам.

**Проверено фактами.** Написан `src/tools/webhid-coverage-honest.js`
с явным списком 14 невозможных маршрутов. Результат:

```
всего маршрутов: 62
доступно в браузере: 48
невозможно: 14

по возможностям: 13 из 17 = 76%
```

**76%, а не 85%.** Применено: документ переписан, цифра исправлена,
в §4 добавлено объяснение, откуда взялась ошибка.

### 2. `protocol.js` использует `Buffer` — в браузере это `ReferenceError` — Severity: Blocker
* **Линза:** `implementation_readiness` 2 (также: `design_critic` 8, `comprehension` 7, `zoom_out` M2)
* **Область:** §4, список «переносятся без изменений»
* **Расхождение:** `src/protocol.js:100–105`, `withReportId()`:

  ```js
  const out = Buffer.alloc(frame.length + 1);
  Buffer.from(frame).copy(out, 1);
  ```

  `Buffer` — глобал Node, в браузере его нет. Это первая функция,
  которую вызовет браузерный клиент, то есть ошибка вылезла бы
  на первом же кадре. Документ утверждал «без изменений».

**Проверено фактами.** `Buffer` встречается только в `protocol.js`
(2 строки) и в `server.js` (не портируется). Остальные 12 модулей
чистые. Проверено grep'ом по всем модулям.

**Применено:** §6.2 даёт точную правку на `Uint8Array` и говорит,
что меняются ровно две строки в одном файле.

### 3. Логика транспорта объявлена «не нужной в браузере», хотя это выстраданные исправления — Severity: Blocker
* **Линза:** `zoom_out` M2 (также: `design_critic` 8, `implementation_readiness` 4, `comprehension` 7)
* **Область:** §4, «transport.js в браузере не нужен»
* **Расхождение:** В `transport.js` только **открытие устройства**
  привязано к Node. Остальное — обычный JS, и это баг-фиксы,
  каждый из которых стоил проекту времени:

  - **батчевое чтение** `BATCH = 64` — наивное «один отчёт за тик»
    теряло 80% пакетов (262 чтения за 4 с вместо 2048, настроек
    2/8 вместо 8/8);
  - **keepalive 2 с** и **announce 15 с**;
  - **оптимистичный кеш после записи** — без него второй вызов
    читает старое значение; именно на этом реверб «не работал»;
  - **фильтр idle-отчётов**;
  - **переподключение с backoff**.

  Объявив файл «не нужным» и не проведя границу, документ обрекает
  браузерный клиент заново зарабатывать те же пять багов.

**Проверено фактами.** `ANNOUNCE_MS = 15000`, `KEEPALIVE_MS = 2000`,
`BATCH = 64`, `reconnect`, `cache.set` после записи — всё на месте.

**Применено:** §6.4 вводит границу «политика транспорта (портируется)
отдельно от адаптера устройства (`node-hid` / `navigator.hid`)»
и перечисляет пять правил.

### 4. Handshake и второй таймер не описаны — клиент увидит устройство без EQ — Severity: Blocker
* **Линза:** `implementation_readiness` 3 (также: `design_critic` 4, `comprehension` 4)
* **Область:** §2, §6 R1, §8 проба
* **Расхождение:** документ свёл поддержку сессии к одному правилу
  «подписка каждые 2 с». Настоящий bootstrap — три отправки и два
  таймера:

  ```
  0x11:0x01 = 1   handshake, ОДИН раз, ДО всего
  0x11:0x24 = 1   подписка, каждые 2 с
  0x11:0x26 = 1   полный дамп: при открытии и повторно каждые 15 с
  ```

  Без handshake — 44 тега вместо 96+. Без **повторного** announce
  не приходят `0x91..0x94` и `0xa1..0xaa` (появляются ~на 19-й секунде).

  Клиент, который возьмёт пример из `research/WEBHID.md` (там только
  подписка, без handshake), увидит устройство без EQ и решит, что
  WebHID не умеет EQ. Это ровно та ошибка, на которую проект уже
  потратил месяц.

**Применено:** §2.4 «Три ловушки» — handshake, брекет микшера,
реверб при Bypass. §9 проба требует проверки на ≥90 тегов и на
появление `0xa1:*` после повторного announce.

### 5. Три ловушки записи не упомянуты — Severity: Major
* **Линза:** `comprehension` 5 (также: `implementation_readiness` 4, 9)
* **Область:** §2, §5, §10
* **Расхождение:** документ перечислял реверб и микшер как доступные,
  не называя условий, без которых они не работают:
  - микшер пишется только пакетом в брекете, порядок критичен;
  - реверб не пишется при `ReverbType = Bypass`;
  - EQ приходит только на первый announce сессии, поэтому

* **Применено:** §2.4 и §9 (проба требует свежей подписки для
  проверки записи).

### 6. Вариант B не даёт 100% без MCC — Severity: Major
* **Линза:** `design_critic` 6 (также: `comprehension` 2, `zoom_out` M1)
* **Область:** §2B, §3 таблица, §8
* **Расхождение:** B приписан «Покрытие: 100%» потому что «агент имеет
  доступ и к USB, и к файлам MCC». Но профили и sample rate — это
  **сам MCC**, а не устройство. То есть 100% достижимы только
  с установленным MCC, а sample rate ещё и с запущенным.
  Проект существует, чтобы MCC не устанавливать — значит B
  в этих двух пунктах возвращает зависимость.
* **Применено:** §3 и §4 показывают **13/17 для обоих вариантов без
  MCC**, и 17/17 для B только с MCC. Добавлена строка в таблицу.

### 7. `navigator.wakeLock` не решает проблему фоновых таймеров — Severity: Major
* **Линза:** `implementation_readiness` 7 (также: `design_critic` 4, `comprehension` 6)
* **Область:** §6 R1
* **Расхождение:** wakeLock удерживает **экран** от выключения и
  освобождается, как только документ становится скрытым — то есть
  именно в том сценарии, от которого защищает. Предложенное лечение
  не может сработать.
  Web Worker помогает частично, но `requestDevice()` доступен только
  в Window — значит нужна модель передачи устройства в воркер.
* **Применено:** §7 R1 переписан: wakeLock назван неработающим,
  описана модель владения (разрешение в окне, устройство в воркере),
  и назван честный откат — «не уходите со вкладки» +
  восстановление сессии при возврате.

### 9. R3 описывает мягкий сценарий вместо опасного — Severity: Major
* **Линза:** `design_critic` 2 (также: `implementation_readiness` 9)
* **Область:** §6 R3
* **Расхождение:** документ говорил «WebHID может не открыть
  устройство — показать ошибку». Опасный случай обратный: устройство
  открывается, запись проходит, но **MCC её откатывает**. Замерено:
  с MCC запись не применялась 60+ секунд, без MCC — 10.

* **Применено:** §7 R3 переписан с требованием детекции:
  после записи — свежий дамп новой подпиской, и при несовпадении
  показать «MCC конфликтует», а не «успех».

## Разрешение

### CONTEST — не применялось, но зафиксировано

Ни одна находка не была оспорена по существу: все проверяемые
обвинения подтвердились фактами (запуском инструментов, чтением кода).

### PROPOSE FIX — применено (все 4 Blocker и 20 Major)

Документ переписан целиком. Главные изменения:

1. Цифра 85% → **76%** по возможностям (13/17), новый инструмент
   `webhid-coverage-honest.js` с явным списком невозможных маршрутов.
2. §6 разбит на три списка: портируется без изменений (12 модулей),
   портируется после правки (`protocol.js`, 2 строки), не портируется.
3. §6.4 — граница «политика транспорта / адаптер устройства» с пятью
   выстраданными правилами.
4. §2.4 — три ловушки: handshake, брекет микшера, реверб при Bypass.
5. §7 R1 — wakeLock назван неработающим, дана модель с воркером
   и честный откат.
6. §7 R3 — требование детекции откатов MCC.
7. §7 R4 — модель угроз и CSP.
8. §7 R7 — File System Access признан возможным.
9. §5 — экономика и версионирование протокола.
10. §9 — восемь проверок «да/нет» для пробы.
11. §3 — упущенные варианты (WebUSB, обёртка Tauri).
12. §10 — полный список оставшегося реверса.
13. Шапка — область Windows.

### ESCALATE

**Какой вариант выбрать.** Документ даёт рекомендацию (A), но
окончательное решение за пользователем: оно зависит от того,
приемлемо ли ограничение «Windows + Chromium» и готов ли проект
потерять смену режима и sample rate. Это не решается кодом.

### DECLINE

- Переписать документ как пошаговый план реализации
  (`implementation_readiness` 1). Это решение об архитектуре,
  а не план работ; пошаговый план появится после выбора варианта.
