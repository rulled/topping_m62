## 1. Как устроены теги в MCC (ФАКТ)

В MCC tag = `(TT << 8) | PP`, и он попадает в кадр как 32-битное число.
Есть **три разных способа** его задать — важно, потому что поиск «просто константы»
даёт мусор.

### 1.1 Прямая таблица «имя параметра → тег»

Функции в диапазоне `0x22be00..0x22e600` реализованы как цепочки сравнений:

```
lea rax, [rip+disp]        ; адрес строки-имени в .rdata
mov [rbp-0x20], rax
call 0x2d330               ; сравнение
test al, al
je   <следующий>
mov dword [rbp-0x10], 0x9b0f   ; <- ТЕГ
jmp  <выход>
```

Это даёт точную карту «человеческое имя → TT/PP». Всего восстановлено
**223 пары, 216 с разрешённым именем.**

### 1.2 Составной тег: `база | номер_канала`

Для микшера и некоторых блоков тег не константа, а собирается:

```
call 0x22c0a0          ; -> номер канала 0..16
or   eax, 0x4100       ; -> база | канал
```

### 1.3 Вложенный диспетчер по имени объекта

Панель микшера идёт через общий сеттер `0x11410(obj, "Mixer_IN12", attr, "L", val)`.
Имя объекта — строка (`Mixer_IN12`, `Mixer_FX`, `Mixer_AUX`…), атрибут — тоже
строка (`Gain`, `MUTE`, `AudioSource`, `GAINLeft`…). Внутри `0x22e530` из пары
(объект, атрибут) вычисляется тег.

## 2. EQ — НАЙДЕН (ФАКТ)

### 2.1 Три эквалайзера

Из строк MCC в одном блоке (`.rdata` 0x00273038):

```
EQ_IN1      <- микрофонный вход 1
EQ_IN2      <- микрофонный вход 2
EQ_HP       <- выход на наушники
```

Подтверждено мануалом M Control Center: «Each microphone input includes a
4-band PEQ» и «The headphone output provides a 10-band PEQ».

### 2.2 Теги EQ

Функция обработки — `0x22f8f0` (конденсатор/дукинг `0x46`), `0x22fb00` (EQ_HP и EQ_IN).

| тег | имя атрибута | назначение |
|---|---|---|
| `0xab0f` | `Switch` | **EQ_HP вкл/выкл** |
| `0xab14` | `GainInputLeft` | EQ_HP входной уровень |
| `0x6303` | `GainOutputLeft` | выход 63 (лево), уровень |
| `0x6403` | `GainOutputLeft` | выход 64 (право), уровень |
| `0x9b0f` | `Switch` | **EQ_IN1 вкл/выкл** |
| `0x9b0d` | `Gain` | EQ_IN1 усиление |
| `0x9b12` | — | EQ_IN1 (второй параметр) |
| `0x9b10` | `Switch` | **EQ_IN2 вкл/выкл** |
| `0x9b0e` | `Gain` | EQ_IN2 усиление |
| `0x9b13` | — | EQ_IN2 (второй параметр) |

Совпадает с прежними находками: `0x9b0f` = `EQ_FX.Switch`, `0xab0f` = `EQ_HP.Switch`.

### 2.3 ЧЕГО В ЭТИХ ТЕГАХ НЕТ — важное ограничение

В HID-протоколе через эти теги передаются только **включение и общий Gain**.
Параметры отдельных полос (тип фильтра `peaking/lowpass/highpass/lowshelf/highshelf`,
частота `Freq`, добротность `Q`) **в этой таблице отсутствуют**.

Строки `peaking`, `lowpass`, `highpass`, `lowshelf`, `highshelf`, `Freq`
в MCC есть (`.rdata` 0x0028ea30+), но относятся к `EqualizerTool` — это
импорт/экспорт CSV-файлов пресетов
(`./Workspace/M62/Prof/EQ_HP_EQSourceFile.csv`), а не к кадру.

**Вывод (факт):** кривая EQ в M62 предположительно считается на стороне ПК и
передаётся не покадрово, либо полосы уходят другим путём (через
`TUSBAUDIO_SetDspProperty`, который mainline-драйвер не использует — см. §4).
**Это не проверено до конца и требует отдельного шага.**

## 3. МИКШЕР — НАЙДЕН (ФАКТ)

### 3.1 Структура

Мануал M62: режим Live streaming — «Mixer: Mix A–E (5 buses)», режим Pro audio —
«Mix A–C (3 buses)». Это подтверждается кодом: базы `0x41..0x48` = 8 шин
(A..H), из которых UI строит 5 или 3.

### 3.2 Каналы (входы микшера) — точный порядок из `0x22c0a0`

Функция возвращает индекс канала по имени `Mixer_<канал><L|R>`:

| имя строки | адрес строки |
|---|---|
| `Mixer_IN12L` / `Mixer_IN12R` | 0x0029dd98 / 0x0029dda8 |
| `Mixer_OTGINL` / `Mixer_OTGINR` | 0x0029ddb8 / 0x0029ddc8 |
| `Mixer_FXL` / `Mixer_FXR` | 0x0029ddd8 / 0x0029dde8 |
| `Mixer_PB12L` / `Mixer_PB12R` | 0x0029ddf8 / 0x0029de08 |
| `Mixer_PB34L` / `Mixer_PB34R` | 0x0029de18 / 0x0029de28 |
| `Mixer_PB56L` / `Mixer_PB56R` | 0x0029de38 / 0x0029de48 |
| `Mixer_PB78L` / `Mixer_PB78R` | 0x0029de58 / 0x0029de68 |
| `Mixer_AUXL` / `Mixer_AUXR` | 0x0029dfe8 / 0x0029dff8 |
| `Mixer_BTL` / `Mixer_BTR` | 0x0029e008 / 0x0029e018 |

**Каналы стереофонические: у каждого есть L и R.** Это принципиально для фронта —
это не «один фейдер на канал», а два.

### 3.3 Атрибуты канала

Из `0x22e530` (имена атрибутов): `GainMLCL`, `GainMLCR`, `GainMRCL`, `GainMRCR`,
`Mix`, `MUTE`, `AudioSource`.

Обозначение: `GainM` + `<L|R канала>` + `<L|R шины>`.
То есть `GainMLCR` = усиление, канал Left, шина Right.

### 3.4 Шины

| база в `or eax` | шина | имя строки |
|---|---|---|
| `0x4100` | Mix A | `MixA` (0x002732a8), цвет `#43CF7C` |
| `0x4200` | Mix B | `MixB` (0x002732c8), цвет `#00AAFF` |
| `0x4300` | Mix C | `MixC` (0x002732e0), цвет `#FFEB3B` |
| `0x4400` | Mix D | `MixD` (0x00274408) |
| `0x4500` | Mix E | `MixE` |
| `0x4600` | Mix F | |
| `0x4700` | Mix G | |
| `0x4800` | Mix H | |

Первые три цвета заданы в коде — это UI-факт, который полезен дизайнеру.

### 3.4A ПРОБЛЕМА: формула даёт коллизию с семейством эффектов

Это найдено при сверке с живым потоком (2026-11-07) и **опровергает**
безусловное чтение формулы из §3.4.

Формула `тег = база_шины | номер_канала`, где номер канала = 0..16, даёт:

| шина | диапазон тегов | что там ещё живёт |
|---|---|---|
| Mix A | `0x4100..0x4110` | — |
| Mix B | `0x4200..0x4210` | — |
| Mix C | `0x4300..0x4310` | — |
| **Mix D** | `0x4400..0x4410` | **эффекты `0x4401..0x440f`** |
| **Mix E** | `0x4500..0x4510` | **`0x4501`, `0x4502` (Chat/Vocal)** |
| Mix F | `0x4600..0x4610` | **компрессор `0x4601..0x4608`** |

Семейство `0x44xx` уверенно опознано как эффекты — не только по таблице имён
MCC, но и по живому потоку: устройство само присылает
`0x44:0x01`=0, `0x44:0x02`=−90, `0x44:0x06`=35, `0x44:0x08`=30,
`0x44:0x09`=4, `0x44:0x0a`=11, `0x44:0x0b`=1.
По таблице имён MCC это `Input1Level`, `Input2Level`, `NoiseReduction`,
`DryWet`, `Room`, `Decay`, `ReverbType`.

**Значит одно из двух:**

1. Номер канала на самом деле не 0..16, а меньше, и `|` не даёт выхода за
   пределы своей сотни; либо
2. База шины — не `0x41..0x48`, и в `or eax, 0x41xx` число означает не шину.

**Что установлено точно:** `or eax, 0x4100..0x4800` в функции `0x22e530`
действительно есть, и рядом лежат строки `MixA..MixD`, `GainMLCL..GainMRCR`.
**Что НЕ установлено:** как именно это превращается в тег на проводе.

Вывод: §3.4 остаётся **описанием кода**, но не доказанной формулой протокола.
Проверять только наблюдением (см. §7).

## 3.5 Второй путь (выходы) — `0x22f5e0`

Функция собирает теги выходов (`0x31..0x34`, `0x51..0x58`, `0x9b..0x98`)
по тому же принципу «база | канал», используя строки
`Mixer_IN12L`, `Mixer_AUXL`, `Mixer_BTL`, `Mixer_OTGINL`, `Mixer_FXL`.

## 4. ПРОТИВОРЕЧИЕ, КОТОРОЕ НАДО ЗАФИКСИРОВАТЬ

Ранее (§1 FINDINGS) было записано, что vendor-контролы идут через
`TUSBAUDIO_GetDspProperty`/`SetDspProperty` из `ToppingProUsbAudioapi_x64.dll`.
Потом (§5A) это было **опровергнуто**: они идут через HID interface 4.

Обе вещи верны **одновременно**: в MCC присутствуют и HID-путь (кадры `22 33 …`),
и импорты `TUSBAUDIO_*DspProperty`. То есть в приложении **два канала управления**:

1. **HID-кадры** — 15 байт, `22 33 20 01 01 TT PP <s32> <CRC> 66 77`.
   Сюда попадают все теги из §1.1, включая EQ-switch и микшер.
2. **Thesycon DSP API** — отдельный вызов DLL. Сюда, судя по отсутствию тегов
   полос в таблице, могут уходить параметры PEQ (тип/частота/Q).

Чем именно из двух управляются полосы EQ — **не установлено**. Для бекенда это
значит: включение EQ и его Gain — гарантированно, а полосы — под вопросом.

## 5. ЧТО ЭТО МЕНЯЕТ ДЛЯ БЕКЕНДА

1. **EQ доступен** — `0x9b0f`, `0x9b10`, `0xab0f` (+ Gain `0x9b0d`, `0x9b0e`, `0xab14`).
2. **Микшер доступен** — 8 шин × 9 каналов × 2 (L/R), теги `0x41NN..0x48NN`.
3. Формула тега микшера: `0x4100 | (шина-1)*0x100 | номер_канала` — **требует
   проверки на живом устройстве**, потому что `or` складывает не так, как выглядит.
   Точная арифметика (`or` над `0x41xx` и индексом канала) даёт коллизии при
   индексах ≥ 0x100, но индексы 0..16 коллизий не дают.
4. Записывать в устройство по-прежнему нельзя без разрешения. Проверка
   любого из тегов микшера/ EQ — это запись.
